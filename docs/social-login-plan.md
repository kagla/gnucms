# 소셜 로그인 도입 계획

## 목표와 범위

첫 릴리스에서는 다음 세 공급자만 지원한다.

| 내부 키 | 화면 이름 | 인증 방식 |
| --- | --- | --- |
| `google` | Google | OAuth 2.0 Authorization Code + OpenID Connect 사용자 정보 |
| `naver` | 네이버 | 네이버 로그인 OAuth 2.0 + 프로필 API |
| `kakao` | 카카오 | 카카오 로그인 OAuth 2.0 + 사용자 정보 API |

GitHub 로그인은 첫 릴리스 범위에서 제외한다. 설정 파일에 GitHub 키가 남아 있어도 공급자
목록과 라우팅에서 활성화되지 않도록 허용 목록을 구글·네이버·카카오 세 개로 제한한다.

공급자 연결 해제, 공급자 계정까지 함께 로그아웃, 한 회원에게 같은 공급자의 여러 계정 연결,
소셜 Access Token을 이용한 다른 API 호출은 첫 릴리스 범위에 포함하지 않는다.

## 현재 구현 상태

프로젝트에는 소셜 로그인의 기본 골격이 이미 있다.

- `GoogleProvider`, `NaverProvider`, `KakaoProvider`가 인가·토큰·프로필 엔드포인트를 정의한다.
- `/auth/{provider}`와 `/auth/{provider}/callback` 라우트가 있다.
- 콜백의 `state` 해시와 만료 시간을 세션에 저장하고 검증한다.
- `(provider, provider_uid)`를 `user_identities`에 저장한다.
- 공급자가 이메일 주소 자체를 주지 않으면 가입·로그인을 차단한다.
- 이메일 주소는 왔지만 공급자가 검증하지 않았다면 사이트 자체 이메일 확인을 거친다.
- 기존 회원과 검증된 이메일이 같으면 기존 계정에 소셜 신원을 연결한다.
- 로그인 완료 시 세션 ID를 재발급한다.

따라서 새 인증 체계를 처음부터 만드는 작업이 아니라, 현재 골격을 세 공급자에 맞게 제한하고
운영·보안·테스트 수준을 보강하는 작업으로 진행한다.

## 공식 연동 기준

- Google: [OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect),
  [OAuth 2.0 웹 서버 애플리케이션](https://developers.google.com/identity/protocols/oauth2/web-server)
- 네이버: [네이버 로그인 개발가이드](https://developers.naver.com/docs/login/devguide/devguide.md),
  [네이버 로그인 개요](https://developers.naver.com/docs/login/overview/overview.md)
- 카카오: [카카오 로그인 이해하기](https://developers.kakao.com/docs/ko/kakaologin/common),
  [카카오 로그인 REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api)

엔드포인트와 동의 항목은 코드에 임의로 추정해 추가하지 않고 위 공식 문서를 기준으로 유지한다.

## 공급자별 처리 방침

### Google

- 요청 범위는 `openid email profile`로 제한한다.
- 사용자 식별자는 변경 가능한 이메일이 아니라 Google의 `sub`를 사용한다.
- `email_verified=true`인 이메일만 기존 계정 자동 연결에 사용할 수 있다.
- 등록된 Redirect URI와 실제 콜백 URI가 스킴, 호스트, 경로까지 정확히 같아야 한다.

### 네이버

- 사용자 식별자는 프로필 응답의 `response.id`를 사용한다.
- 이메일과 별명은 네이버 개발자센터에서 사용 API 및 제공 정보로 승인된 경우에만 온다고 본다.
- 네이버 프로필 응답의 이메일은 네이버가 제공한 계정 이메일로 신뢰한다.
- 이메일이 없으면 가입과 로그인을 차단한다.

### 카카오

- 사용자 식별자는 사용자 정보 응답의 `id`를 사용한다.
- 인가 URL에서 선택 동의 항목을 강제로 요청하지 않고 카카오디벨로퍼스 앱 설정을 따른다.
- 닉네임이 없으면 `카카오 회원`을 표시 이름으로 사용한다.
- 이메일은 `is_email_valid`와 `is_email_verified`가 모두 참일 때만 신뢰한다.
- 이메일 제공 동의를 받지 못해 주소가 없으면 로그인하지 않는다.
- 주소는 있지만 검증되지 않았다면 사이트 자체 이메일 확인을 거친다.

## 네이버·카카오 운영 연결 절차

### 네이버 개발자센터

1. 애플리케이션에서 네이버 로그인 API를 사용하도록 설정한다.
2. 제공 정보에서 이메일을 필수로 설정하고, 별명은 필요할 때만 허용한다.
3. 서비스 URL과 관리자 화면에 표시된 `/auth/naver/callback` 주소를 Callback URL로 등록한다.
4. 발급된 Client ID와 Client Secret을 `사이트 설정 → 소셜 로그인 → 네이버`에 저장하고
   `네이버 로그인 사용`을 켠다.

네이버 프로필 응답에 이메일이 있으면 검증된 이메일로 사용한다. 이메일, 정상 `resultcode=00`,
사용자 식별자 중 하나라도 없으면 로그인에 실패한다.

### 카카오디벨로퍼스

1. 앱의 카카오 로그인을 활성화한다.
2. 플랫폼 키에서 JavaScript 키가 아닌 **REST API 키**를 확인한다.
3. 관리자 화면에 표시된 `/auth/kakao/callback` 주소를 Redirect URI로 등록한다.
4. 카카오계정(이메일)은 필수 동의로 설정하고, 닉네임은 필요할 때만 설정한다.
5. REST API 키를 `사이트 설정 → 소셜 로그인 → 카카오`에 저장하고
   `카카오 로그인 사용`을 켠다.

카카오디벨로퍼스의 REST API 키용 Client Secret 기능이 ON이면 같은 화면에 해당 Client Secret도
입력해야 한다. 기능이 OFF이면 입력하지 않으며, 이전에 잘못 저장했다면 `저장된 Client Secret 삭제`로
제거한다. REST API 키와 Client Secret은 반드시 같은 앱에서 발급된 값이어야 한다.

카카오는 `is_email_valid`와 `is_email_verified`가 모두 참인 이메일만 즉시 신뢰한다. 이메일 주소가
있지만 어느 하나가 거짓이면 사이트 자체 이메일 확인으로 이어진다. 이메일 주소 자체가 없거나 사용자
식별자인 최상위 `id`가 없는 응답은 로그인에 사용하지 않는다.

두 공급자 모두 인가 요청의 `state`를 단회 검증하며 Access Token과 Refresh Token은 프로필 조회가
끝난 뒤 DB나 세션에 저장하지 않는다.

## 설정 구조

관리자 화면의 `사이트 설정 → 소셜 로그인` 탭에서 자격 증명과 사용 여부를 관리한다.
값은 별도 테이블 없이 기존 `site_settings`에 `oauth.*` 키로 저장하며 Client Secret은
`auth.secret`에서 파생한 키로 암호화한다. `config/config.php` 값은 DB 설정이 아직 없을 때의
호환용 기본값으로 계속 사용할 수 있다.

각 공급자 설정에는 공식 키 발급·관리 화면으로 이동하는 링크를 제공한다.

- Google: `https://console.cloud.google.com/auth/clients`
- 네이버: `https://developers.naver.com/apps/#/list`
- 카카오: `https://developers.kakao.com/console/app`

카카오 설정 영역에는 이메일 제공 동의 절차를 펼침 안내로 함께 제공한다. 사용 설정, Redirect URI,
카카오계정(이메일) 필수 동의, 동의 화면 미리보기 순서를 설명하고, 필수 동의 권한이 비활성화된 경우
비즈 앱 전환과 `앱 → 추가 기능 신청 → 개인정보 동의항목` 심사 절차 및 공식 문서 링크를 안내한다.

```php
'oauth' => [
    'google' => ['client_id' => '', 'client_secret' => ''],
    'naver'  => ['client_id' => '', 'client_secret' => ''],
    'kakao'  => ['client_id' => '', 'client_secret' => ''],
],
```

사용 스위치가 켜져 있고 `client_id`, `client_secret`, `redirect_uri` 세 값이 모두 준비된
공급자만 로그인 화면에 노출한다.
`redirect_uri`를 생략하면 `app.url`을 기준으로 다음 주소를 만든다.

```text
{app.url}/auth/google/callback
{app.url}/auth/naver/callback
{app.url}/auth/kakao/callback
```

- 운영 환경의 `app.url`은 반드시 외부에서 접근 가능한 HTTPS 주소여야 한다.
- Client Secret은 저장소에 커밋하지 않고 DB에는 암호문으로만 저장한다.
- 샘플 설정과 설치기가 생성하는 설정에서는 빈 값만 제공한다.
- 환경 변수 직접 지원은 후속 과제로 두되, 배포 환경이 필요로 하면 설정 파일보다 우선하도록 추가한다.

사이트 설정의 로그인·가입 정책은 방식마다 두 스위치로 나눈다.

- `password_login_enabled`: 일반 회원의 이메일·비밀번호 로그인
- `social_login_enabled`: 활성 공급자를 이용한 소셜 로그인
- `registration_enabled`: 이메일·비밀번호를 이용한 신규 일반 회원가입
- `social_registration_enabled`: 활성 공급자를 이용한 신규 소셜 회원 생성

로그인 스위치를 끄면 같은 방식의 신규 가입 스위치도 자동으로 꺼지고 비활성화된다. 이 종속
관계는 화면뿐 아니라 저장과 실제 인증 경로에서도 강제한다. 가입 스위치만 끈 경우에는 기존
회원의 해당 방식 로그인이 유지된다. 공급자별 `oauth.{provider}.enabled`를 끄면 전체 소셜 로그인
스위치와 별개로 해당 공급자만 닫힌다. 두 가입 스위치가 모두 꺼졌을 때 회원가입 링크와
`/register` 화면을 닫는다.

일반 회원 로그인을 꺼도 관리자 비밀번호 로그인은 사이트 잠금을 막기 위해 유지한다. 소셜 로그인은
꺼진 즉시 시작·콜백·이메일 확인 완료 단계에서 모두 차단한다. 기존 설치는 새 로그인 스위치가
없으므로 두 방식을 허용한 상태로 이전하고, 하나였던 `registration_enabled` 값은 새 소셜 가입
스위치에도 복사해 종전의 가입 차단 선택을 보존한다.

## 계정 연결 규칙

계정 연결의 단일 키는 `(provider, provider_uid)`다. 이메일은 연결을 돕는 속성이지 소셜 신원의
기본 키가 아니다.

1. `(provider, provider_uid)`가 이미 있으면 연결된 회원으로 로그인한다.
2. 신원이 없고 공급자가 검증한 이메일이 기존 회원과 같으면 그 회원에게 연결한다.
3. 검증된 이메일에 해당하는 회원이 없으면 새 회원과 신원을 한 트랜잭션에서 만든다.
4. 이메일이 없으면 중단하고, 주소는 있지만 신뢰할 수 없으면 사이트 확인 메일을 보낸다.
5. 확인 링크가 완료된 뒤에만 기존 계정 연결 또는 신규 회원 생성을 수행한다.
6. 이름이나 별명만으로 계정을 합치지 않는다.
7. 정지 회원에 연결된 신원은 로그인을 허용하지 않는다.
8. 신규 소셜 가입은 첫 관리자 선점 플래그를 변경하지 않는다.

소셜 가입은 첫 관리자 자리를 선점할 수 없게 변경한다. 첫 관리자는 설치기 또는 별도로 보호된
로컬 가입 절차에서만 만들 수 있어야 한다. 관리자가 아직 없는 설치에서는 신규 소셜 가입을
거절하고 관리자 설치를 먼저 완료하도록 안내한다. 외부 공급자 로그인을 켜 둔 채 먼저 접속한
사람이 관리자 권한을 얻는 경로를 남기지 않는다.

## 데이터베이스

새 테이블은 만들지 않는다. 현재 `user_identities`가 필요한 관계를 이미 표현한다.

```text
user_id
provider
provider_uid
created_at
UNIQUE(provider, provider_uid)
INDEX(user_id)
```

한 회원이 구글·네이버·카카오 신원을 각각 연결할 수 있으므로 공급자 컬럼을 `users`에 합치지
않는다. Access Token과 Refresh Token은 로그인 완료 후 저장하지 않는다.

추가로 검토할 무결성 규칙은 `UNIQUE(user_id, provider)`다. 한 회원에게 같은 공급자의 신원을
여러 개 연결하는 기능을 제공하지 않을 계획이면 이 제약을 추가한다. 여러 Google 계정 연결 같은
기능을 지원할 가능성이 있다면 현재 구조를 유지한다. 1차 릴리스에서는 한 회원당 공급자별 한
신원으로 제한하는 쪽을 권장한다.

## 보안 요구사항

- Authorization Code Flow만 사용하고 브라우저에 Access Token을 노출하지 않는다.
- 32바이트 이상 난수로 `state`를 만들고 서버 세션에는 해시만 저장한다.
- `state`는 한 번 검증한 즉시 삭제하며 짧은 만료 시간을 적용한다.
- 여러 탭에서 동시에 로그인할 수 있도록 공급자별 한 건이 아니라 여러 미완료 `state`를 안전하게
  보관하는 구조를 검토한다.
- 콜백 URI는 서버가 구성한 고정값만 사용하며 요청 파라미터로 받지 않는다.
- 로그인 완료 시 `session_regenerate_id(true)`를 실행한다.
- 공급자 오류 원문, 인증 코드, Access Token, Client Secret을 화면이나 일반 로그에 남기지 않는다.
- 사용자에게는 공통 오류 메시지를 보여 주고 서버 로그에는 토큰을 제외한 공급자와 실패 단계만 남긴다.
- 자체 이메일 확인 발송에는 IP·세션 기반 재전송 제한을 둬 메일 발송 악용을 막는다.
- 이메일 확인 링크는 현재처럼 세션에 묶어 단회 사용한다. 다른 기기에서 확인하는 요구가 생기면
  세션 저장 대신 만료·사용 시각이 있는 별도 단회 토큰 저장 방식으로 확장한다.
- 공급자에서 받은 이름·이메일도 외부 입력으로 보고 길이와 형식을 검증한다.

PKCE는 세 공급자의 지원 범위와 사용 중인 OAuth 클라이언트 라이브러리를 확인한 뒤 공통 적용한다.
일부 공급자에만 임의 적용해 흐름을 갈라놓지 않는다.

## 개인정보와 동의

- 로그인에 필요한 최소 정보인 공급자 UID, 이메일, 표시 이름만 요청한다.
- 프로필 사진은 공급자가 제공하면 최초 연결 시 사이트 저장소로 복사한다. 사용자는 회원가입 및 회원정보 수정에서 JPG·PNG·WebP 이미지를 직접 등록·교체·삭제할 수 있고, 직접 올린 이미지는 이후 소셜 로그인으로 덮어쓰지 않는다.
- 성별, 생일, 전화번호 등은 요청하거나 저장하지 않는다.
- 소셜 신규 가입에도 일반 가입과 같은 필수 약관을 적용한다.
- 체크박스를 직접 보여 주지 않는 소셜 흐름은 현재처럼 로그인 버튼 주변에 동의 고지를 표시하고,
  필수 약관만 동의로 기록하며 선택 약관은 동의하지 않음으로 기록한다.
- 개인정보 처리방침에 공급자별 수집 항목, 이용 목적, 보유 기간, 연결 해제 방법을 명시한다.

## 로그인 이력과 회원 탈퇴

- 비밀번호와 소셜 로그인 모두 성공·실패 시도마다 `login_events`에 한 행을 누적한다.
- 로그인 방식, 결과, 회원 ID(알 수 있을 때), 입력 식별자, 접속 IP, User-Agent, 시각을 기록한다.
- `password_attempts`는 단기 실패 제한용 집계이고 `login_events`는 사후 확인용 감사 이력이므로
  서로 합치거나 성공 시 삭제하지 않는다.
- 소셜 전용 회원은 회원 탈퇴 직전에 현재 연결된 공급자로 다시 인증한다.
- 탈퇴하면 소셜 연결을 삭제하여 같은 공급자 UID와 이메일로 새 회원 가입을 허용한다. 새 회원은
  기존 글·댓글·로그인 이력과 다시 연결하지 않는다.
- 탈퇴 회원의 로그인 이력은 유지하되 이메일 등 `login_identifier`는 비워 직접 식별을 줄인다.
  당시 IP, 방식, 결과, 시각은 운영상 사후 확인을 위해 유지한다.

## 화면 방향

- 노출 순서는 Google → 네이버 → 카카오로 고정한다.
- 설정이 완성된 공급자만 로그인·회원가입 화면에 표시한다.
- 공식 브랜드 가이드에 맞는 버튼 문구와 색상·로고를 사용하되, 로고 파일의 사용 조건을 확인한다.
- 문구는 각각 “Google로 계속하기”, “네이버로 계속하기”, “카카오로 계속하기”로 통일한다.
- 공급자 취소, 이메일 미제공, 계정 정지, 확인 메일 만료를 서로 구분해 안내한다.

## 구현 순서

### 1. 공급자 범위 고정

- `ProviderRegistry` 허용 목록을 `google`, `naver`, `kakao`로 제한한다.
- `App`의 자동 콜백 생성 목록도 세 공급자로 제한한다.
- 설치기와 `config.sample.php`에서 GitHub 설정을 제거한다.
- 로그인 템플릿의 임시 문자 로고를 공식 자산 또는 프로젝트 자산으로 교체한다.

### 2. 공급자 프로필 검증 강화

- 공급자 UID가 비어 있으면 로그인 실패로 처리한다.
- 이메일 길이·형식과 검증 여부를 공급자별로 명시적으로 매핑한다.
- 네이버·카카오 응답에서 필드가 누락되는 경우를 정상 분기로 처리한다.
- Google은 `sub`, 네이버는 `response.id`, 카카오는 최상위 `id`를 사용한다.

### 3. 보안과 오류 처리

- State 만료·단회 사용·다중 탭 동작을 테스트한다.
- 이메일 확인 재발송 제한을 추가한다.
- 공급자 통신 오류를 사용자 메시지와 안전한 내부 기록으로 분리한다.
- 세션 고정 공격 방지와 정지 회원 차단을 회귀 테스트한다.

### 4. 공급자 콘솔 설정과 운영 문서

- 개발·스테이징·운영 콜백 URI를 각각 등록한다.
- 네이버에서 이메일·별명 제공 항목을 확인하고, 카카오 이메일·닉네임이 필요하면 동의항목을 설정한다.
- Google 동의 화면의 앱 이름, 도메인, 개인정보 처리방침 주소를 등록한다.
- Client Secret 교체 절차와 장애 시 해당 공급자만 끄는 방법을 운영 문서에 기록한다.

### 5. 테스트와 출시

- 단위 테스트에서는 실제 외부 통신 대신 공급자 응답을 고정해 매핑을 검증한다.
- 웹 테스트에서는 시작 → 콜백 → 계정 연결 → 세션 생성 전체 흐름을 검증한다.
- 각 공급자의 개발 앱으로 실제 로그인 스모크 테스트를 수행한다.
- 한 공급자의 장애가 비밀번호 로그인과 다른 공급자 로그인에 영향을 주지 않는지 확인한다.

## 필수 테스트 목록

- 설정된 세 공급자만 화면에 정해진 순서로 보인다.
- GitHub 설정을 넣어도 첫 릴리스에서는 활성화되지 않는다.
- 변조·누락·만료·재사용된 `state`가 모두 거절된다.
- 빈 인증 코드와 공급자 취소가 안전하게 처리된다.
- Google의 검증된 이메일은 신규 가입 및 기존 회원 연결에 사용된다.
- 네이버 이메일은 자체 확인 전까지 기존 회원에게 연결되지 않는다.
- 카카오의 유효·검증 이메일만 신뢰한다.
- 이메일이 없는 Google·네이버·카카오 계정은 가입·로그인을 차단한다.
- 주소는 있지만 검증되지 않은 소셜 이메일만 자체 확인 화면으로 이동한다.
- 동일 `(provider, provider_uid)`로 재로그인해 회원이 중복 생성되지 않는다.
- 동일 이메일의 로컬 회원과 안전하게 연결된다.
- 정지 회원은 소셜 신원이 일치해도 로그인할 수 없다.
- 관리자가 없는 설치에서 소셜 가입으로 관리자 계정을 만들 수 없다.
- 로그인 성공 시 세션 ID가 바뀐다.
- 필수·선택 동의 기록과 IP·User-Agent 증적이 기존 정책대로 남는다.
- 공급자 또는 메일 장애 시 중간 회원·신원 행이 남지 않는다.
- 비밀번호·소셜 로그인 성공과 실패가 IP·User-Agent와 함께 계속 누적된다.
- 소셜 회원이 공급자 재인증 후 탈퇴할 수 있고 같은 이메일·소셜 계정으로 새 가입할 수 있다.

## 완료 기준

- 운영 로그인·회원가입 화면에는 Google, 네이버, 카카오만 표시된다.
- 세 공급자 모두 실제 개발 앱에서 신규 가입과 재로그인이 성공한다.
- 신뢰할 수 없는 이메일은 자체 확인 없이는 계정에 연결되지 않는다.
- 비밀번호 로그인과 기존 회원 데이터에 회귀가 없다.
- 외부 토큰과 평문 Client Secret이 DB, 세션 영속 데이터, 화면, 로그에 남지 않는다.
- SQLite, MySQL/MariaDB 테스트와 전체 PHPUnit 테스트가 통과한다.

## 이번 문서에서 정한 결정

- 첫 공급자는 Google, 네이버, 카카오 세 개로 제한한다.
- 기존 OAuth 골격과 `user_identities`를 재사용하며 새 테이블은 추가하지 않는다.
- GitHub 로그인은 첫 범위에서 제거한다.
- 네이버 및 신뢰할 수 없는 카카오 이메일은 사이트 자체 확인을 거친다.
- 소셜 가입으로 첫 관리자 권한을 획득할 수 없게 한다.
- 자격 증명은 관리자 소셜 로그인 탭에서 관리하며 기존 설정 파일은 기본값으로 호환한다.

## 구현 반영 상태

현재 코드에는 다음 항목까지 반영했다.

- 공급자 허용 목록과 라우트를 Google, 네이버, 카카오로 제한
- 설치기와 샘플 설정에서 GitHub 제거
- 공급자 노출 순서를 Google → 네이버 → 카카오로 고정
- 소셜 신규 가입의 첫 관리자 선점 차단
- 공급자 프로필의 공급자 키 일치 검증
- 공급자별 프로필 UID 및 이메일 검증 여부 매핑 테스트
- 공급자별 최대 5개의 OAuth `state`, 10분 만료, 단회 사용 및 다중 탭 지원
- 자체 이메일 확인 메일의 1분 재발송 제한
- 이메일 미제공 소셜 계정의 가입·로그인 차단 및 기존 임의 이메일 생성 제거
- 미지원 공급자 라우트 차단과 전체 OAuth 웹 흐름 테스트
- 관리자 설정 탭에서 공급자별 사용 여부와 자격 증명 저장
- 비밀번호·소셜 로그인 성공/실패 감사 이력 누적 및 관리자 회원 화면 최근 20건 표시
- 일반 회원 가입 IP, 탈퇴 시각과 탈퇴 IP 저장
- 비밀번호 회원의 현재 비밀번호 확인 및 소셜 회원의 공급자 재인증을 거친 회원 탈퇴
- 탈퇴 시 이메일·표시 이름·글/댓글 작성자 비식별화, 소셜 연결 삭제, 이메일·소셜 계정 재사용 허용
- Client Secret 암호화 저장 및 저장된 비밀값 화면 비노출
- 카카오 선택 동의항목 강제 요청 제거, Client Secret 선택 입력 및 저장값 삭제 지원
- 기본·홈, 회원·글쓰기, 소셜 로그인, 메일, 시스템·유지보수 설정 화면 분리

실제 출시 전에는 공급자별 개발자 콘솔 등록, 운영 Client ID·Secret 주입, HTTPS 콜백 등록,
Google·네이버·카카오 개발 앱을 이용한 외부 스모크 테스트가 남아 있다.
