# 알리고 알림톡·문자 발송 코어 내장 — 설계

> 과거 계획·작업 기록입니다. 작성 당시의 제안·검증 결과는 보존하며 현재 기능 제공을 보장하지 않습니다. 현재 지원 범위는 [공개 매뉴얼](https://gnucms.com/manual/support)과 [지원 범위 문서](https://github.com/kagla/gnucms/blob/main/docs/supported-features.md)를 따릅니다. 백업·확장·쇼핑몰은 현재 코어에 구현되어 있으며 자동 복원·자동 DB 백업은 제공하지 않습니다.

2026-09-17. 브랜치 `feat/aligo-messaging`.

## 목표

1. **알리고**(smartsms.aligo.in) 계정으로 카카오 **알림톡**과 **문자(SMS·LMS)** 를 보내는 기능을 GNUCMS 코어에 넣는다. 관리자가 화면에서 직접 보내고, 코어 알림(비밀번호 재설정 등)도 같은 엔진으로 나간다.
2. 확장(모듈·플러그인)이 자기 대상에게 일괄 발송할 수 있도록 **공개 발송 API**를 제공한다. 영카트 모듈이 "선택한 주문의 주문자에게 일괄 발송"을 만들 때 이 API만 쓰면 된다.
3. 회원에게 보내려면 연락처가 필요하므로 `users`에 **휴대폰번호**를 더하고, 코어 알림을 메일·알림톡·문자·알림함으로 나눠 보내는 **알림 채널 배선**을 만든다.
4. 새 Composer 의존성은 추가하지 않는다. 호스팅 cron을 요구하지 않는다.

## 0. 배경과 결정

- 알리고는 **알림톡 API**(`kakaoapi.aligo.in`)와 **문자 API**(`apis.aligo.in`)가 서로 다른 서비스다. 호스트·인증 파라미터 이름·응답 필드·인코딩이 모두 다르므로 호출부는 나누고, 발송 작업·수신자·결과·번호 처리는 한 살림으로 쓴다.
- **문자가 알림톡보다 많이 쓰일 것으로 본다.** 알림톡은 카카오 템플릿 승인에 4~5일이 걸리고 승인된 본문을 벗어날 수 없는 반면, 문자는 관리자가 본문을 바로 써서 보낸다. 따라서 문자는 알림톡의 대체 수단이 아니라 **동등한 1급 채널**로 설계한다.
- 이 작업은 `feat/initalk`의 **비즈뿌리오** 메시징(`src/Messaging/`, `bp_*` 테이블, `Schema::VERSION` 23)과 **독립적으로** 만든다. 사용자 결정이다. 두 브랜치를 모두 main에 넣으려면 나중에 알림톡 서브시스템이 두 벌이 되고 스키마 판 23이 충돌하므로, 그때 어느 한쪽을 고르거나 공급자 추상화로 합치는 별도 작업이 필요하다. 이 설계는 그 통합을 다루지 않는다.
- 범위를 한 브랜치에 모두 넣되(사용자 결정) 아래 3단계로 나눠 각 단계 끝에서 테스트로 검증한다.
  1. 알리고 연동과 발송 엔진 (`src/Aligo/`, 표 3장, 관리자 화면)
  2. 회원 휴대폰번호 (`users.phone`, 가입·회원정보·관리자 화면)
  3. 알림 채널 배선 (`src/Notify/`, 코어 알림 전환)

### 확정한 범위

| 항목 | 결정 |
|---|---|
| 공급자 | 알리고만. 공급자 선택 추상화는 만들지 않는다 |
| 알림톡 템플릿 | 알리고에서 **가져오기만**. 작성·수정·삭제·검수요청은 하지 않는다 |
| 카카오채널 등록 | 하지 않는다. 발신프로필키는 `/profile/list/`로 **조회해 고른다** |
| 문자 | SMS·LMS. **MMS(이미지 첨부)는 넣지 않는다** |
| 예약 발송 | **넣는다**(알림톡 `senddate`, 문자 `rdate`·`rtime`). 취소도 함께 넣는다 — 예약을 걸 수 있는데 멈출 방법이 없으면 잘못 건 대량 발송을 되돌릴 수 없다. 2026-09-18 사용자 결정으로 처음의 "넣지 않는다"를 뒤집었다. §5-1 참고 |
| 대체발송 | 알림톡 실패 시 문자 대체발송(`failover`)을 **발송마다 선택**할 수 있다 |
| 수신자 지정 | 회원 검색·선택, 번호 직접 입력·붙여넣기. **CSV 업로드는 넣지 않는다** |
| 휴대폰번호 | 입력만 받는다. **인증번호 본인확인은 하지 않는다** |
| 수신동의 | 별도 동의 항목을 만들지 않는다. 정보성 발송을 전제한다 |
| 결과 수신 | 알리고는 웹훅이 없다. **방문 기반 폴링**으로 갱신한다 |

## 3. 알리고 API 연동

모든 호출은 form-urlencoded POST다. `Transport`가 실행하고 각 Api 클래스가 인증 파라미터와 응답 판정을 맡는다.

### 알림톡 (`kakaoapi.aligo.in`, `apikey`·`userid`, UTF-8)

| 용도 | 경로 |
|---|---|
| 잔여 건수·연결 확인 | `/akv10/heartinfo/` |
| 카카오채널 목록 | `/akv10/profile/list/` |
| 템플릿 목록 | `/akv10/template/list/` |
| 발송 | `/akv10/alimtalk/send/` |
| 결과 상세 | `/akv10/history/detail/` |

응답 `code`가 `0`이면 정상이다. 그 밖은 `ResultCodes`가 사유로 바꿔 `DomainError`로 올린다.

### 문자 (`apis.aligo.in`, `key`·`user_id`, EUC-KR)

| 용도 | 경로 |
|---|---|
| 잔여 건수·연결 확인 | `/remain/` |
| 발송 | `/send_mass/` |
| 결과 상세 | `/sms_list/` |

응답 `result_code`가 `1`이면 정상, 음수면 실패다(`message`에 사유가 온다).

**문자는 `/send_mass/` 하나만 쓴다.** `/send/`가 1천명까지 되지만 본문이 전원 같을 때만 쓸 수 있다. 수신자별 변수 치환을 지원하려면 `/send_mass/`가 필요하고, 코드 갈래를 둘로 두느니 500명씩 나누는 편이 단순하다.

### 인코딩

문자 API는 EUC-KR이다. `MessageText`가 본문·제목을 EUC-KR로 변환해 바이트를 재고 그 형태로 보낸다.

- **SMS**는 90바이트 이하, 넘으면 **LMS**로 자동 전환한다. LMS는 2,000바이트까지, 제목은 44바이트까지다.
- EUC-KR로 변환되지 않는 글자(이모지 등)가 있으면 **보내기 전에 거절하고 어느 글자인지 알린다.** 깨진 문자를 내보내지 않는다.
- 알림톡 본문은 UTF-8 그대로 보낸다. 대체발송 본문만 EUC-KR 규칙을 탄다.

### 연결 확인

설정 화면의 **연결 확인**이 `heartinfo`와 `remain`을 함께 불러 "키가 맞고, 알림톡 N건·SMS N건·LMS N건 남았습니다"까지 한 줄로 보여준다. 키 유효성과 발송 가능 여부를 한 번에 확인하기 위해서다.

## 4. 발송

```php
$app->aligo()->send([
    'channel'  => 'sms',            // 'at' | 'sms'  ('lms'는 길이로 자동 판정)
    'body'     => '#{이름}님, 주문 #{주문번호}이 발송되었습니다.',
    'title'    => '배송 안내',       // LMS로 넘어갈 때만 쓴다
    'tpl_code' => null,             // 알림톡이면 필수
    'failover' => false,
    'recipients' => [
        ['phone' => '01012345678', 'name' => '홍길동', 'vars' => ['이름' => '홍길동', '주문번호' => 'A-1001']],
        ['phone' => '01098765432', 'name' => '김철수', 'vars' => ['이름' => '김철수', '주문번호' => 'A-1002']],
    ],
]): int   // message_jobs.id
```

영카트 같은 모듈은 선택한 주문에서 이 배열만 만들어 넘긴다.

처리 순서:

1. 채널 발송 허용 스위치를 확인한다. 꺼져 있으면 발송하지 않고 거절한다. **확장이 부르는 경로도 같은 스위치를 지난다.**
2. 번호를 `PhoneNumber`로 정규화하고 국내 휴대폰 형식이 아닌 것은 거절한다. 같은 번호가 여러 번 들어오면 한 번만 보낸다.
3. 본문의 `#{...}`를 수신자별 `vars`로 치환한다. **값이 없는 변수가 하나라도 있으면 작업 전체를 만들지 않고 거절하며, 어느 수신자의 어느 변수가 비었는지 알린다.** 일부만 보내고 나머지를 실패로 남기지 않는다 — 빈 값으로 보내면 알림톡은 `rslt: U`(템플릿 불일치)로 떨어지고 문자는 뜻이 깨진 채로 나간다.
4. 알림톡이면 켜진 승인 템플릿인지 확인한다. 문자면 `MessageText`가 SMS·LMS를 판정한다.
5. `message_jobs` 한 건과 `message_recipients` 여러 건을 만든다.
6. **500명씩 나눠** API를 부른다. 응답의 `mid`를 그 묶음의 수신자 행에 적고 `success`·`failure`를 누적한다.
7. **발송은 재시도하지 않는다.** 응답을 못 받은 묶음은 `failed`로 두고 사유를 남긴다. 재시도하면 중복 발송이 되기 때문이다. 조회 계열만 재시도한다.

테스트 모드가 켜져 있으면 알림톡은 `testMode=Y`, 문자는 `testmode_yn=Y`로 보낸다. 실제 발송과 과금 없이 나머지가 똑같이 동작하므로 파라미터를 검증할 수 있다. 그렇게 보낸 작업은 이력에 **테스트**로 표시한다.

## 5. 결과 갱신

알리고는 결과 웹훅이 없다. `docs/extensions.md`가 호스팅 cron을 요구하지 말라고 정하고 있으므로 **방문 기반**으로 갱신한다.

- 관리자가 이력 화면을 열 때, 결과가 아직 안 잡힌 `mid` 가운데 마지막 조회로부터 일정 시간(60초)이 지난 것을 갱신한다. 한 번 열 때 알리고에 묻는 횟수는 **최대 5번**이고, 알림톡 결과 대기열과 대체문자 결과 대기열이 이 예산을 나눠 쓴다 — 두 대기열을 합쳐 5번을 넘지 않는다. 화면 하나가 API를 오래 붙잡지 않기 위해서다.
- 알림톡은 `/akv10/history/detail/`, 문자는 `/sms_list/`를 `mid`로 부르고 수신자별 결과를 `msgid`(문자는 `mdid`)로 맞춰 적는다.
- 관리자 여럿이 동시에 열어도 같은 `mid`를 중복 조회하지 않도록 짧은 잠금을 건다.
- 결과 대기 중인 작업이 있으면 화면에 **"아직 결과를 기다리는 중"** 을 명시하고 갱신 버튼을 둔다. 접속이 없으면 늦어질 수 있다는 사실을 숨기지 않는다.
- cron을 쓸 수 있는 환경을 위해 `bin/messages.php`를 두어 같은 갱신을 CLI로 돌릴 수 있게 한다. **없어도 동작한다.**
- 보낸 지 오래됐는데도 결과가 안 잡히는 건은 일정 기간(7일) 뒤 조회를 멈추고 `불명확`으로 남긴다. 무한히 조회하지 않는다.

## 5-1. 예약 발송과 취소

예약을 걸면 메시지는 **그 순간 알리고로 넘어간다.** 발송 허용 스위치도 템플릿 승인도 예약을 거는 시점에만 확인할 수 있고, 실제 나가는 시점에는 이미 우리 손을 떠나 있다. 이 절의 규칙은 전부 그 사실에서 나온다.

- `message_jobs`에 `scheduled_at`(비어 있으면 즉시 발송)과 `cancelled_at`을 더한다. 작업 상태에 `scheduled`와 `cancelled`가 붙어 일곱 개가 된다.
- **예약 시각이 아직 오지 않은 작업은 수신자 집계와 무관하게 `scheduled`다.** 알리고가 접수했지만 결과가 없는 것이 정상이므로, 이것을 §5의 "대기 중" 규칙에 섞으면 이력이 거짓말을 한다.
- 발송 시각은 **현재 +10분 이후, 30일 이내**여야 한다. 하한은 알리고 문자 API가 요구하는 값이고 두 채널에 같은 규칙을 쓴다. 상한은 업체 문서에 없어 우리가 정한다 — 무제한 예약은 잊힌 채 나가는 사고를 부른다.
- **포기 시한은 `scheduled_at` 기준으로 센다.** `requested_at` 기준이면 5일 뒤로 예약한 작업이 나가기도 전에 `불명확`이 된다.
- **발송 시각이 안 된 작업은 결과 조회 대상에서 뺀다.** 알리고가 아직 보내지도 않은 건에 §5의 조회 예산을 쓰지 않는다.
- 취소는 알림톡 `/akv10/cancel/`, 문자 `/cancel/`로 하며 둘 다 `mid` 하나를 받는다. **발송 5분 전까지만 가능하다.**
- 500명이 넘는 작업은 `mid`가 여러 개라 일부만 취소될 수 있다. **그 부분 실패를 그대로 보여준다** — "3개 묶음 중 2개 취소, 1개는 취소하지 못했습니다". **화면은 개수만 말하고 원인은 단정하지 않는다**: 취소는 시한 초과 말고도 통신 실패·키 취소·미등록 IP 로 거절되고, 알림톡 응답 코드표에는 시한 초과를 가리키는 코드 자체가 없어 가려낼 수도 없다. 알리고가 돌려준 사유는 그 묶음의 수신자 행에 적혀 **이력 상세의 수신자별 "사유" 칸**에 보인다 — 틀린 원인("시한이 지났습니다")은 다시 시도하지 말라는 지시가 되어, 다시 눌렀으면 멈출 수 있었을 발송을 내보낸다.
- 채널 발송 허용을 끄면 그 채널의 예약을, 템플릿이 승인을 잃으면 그 템플릿으로 건 예약을 **자동으로 취소 요청한다.** 시한을 지나 실패한 건은 화면에 그대로 알린다 — 조용히 넘어가면 관리자는 막힌 줄 안다.
- 확장도 `send(['scheduled_at' => ...])`로 예약할 수 있다. 같은 하한·상한과 같은 발송 허용 스위치를 지난다.

## 6. 알림 채널 배선

```php
$this->notifier->notify('password_reset', Recipient::forUser($user), [
    '이름' => $user['display_name'], '사이트명' => $siteName, '링크' => $resetUrl, '유효시간' => '30분',
]);
```

`Notifier`가 `NotifySettings`에서 그 이벤트에 켜진 채널을 읽어 차례로 보낸다.

- **한 채널이 실패해도 나머지는 보낸다.** 실패는 기록한다.
- **모든 채널이 실패하면 예외를 올린다.** 아무 데도 안 갔는데 화면이 "보냈습니다"라고 하면 안 된다.
- 알림톡·문자 채널은 받는 사람의 휴대폰번호가 없으면 **조용히 건너뛴다.** 실패로 기록하지 않는다 — 번호를 내지 않은 회원이 실패 이력을 쌓을 이유가 없다.

### 이벤트

| 키 | 라벨 | 알림톡·문자 | 지금 위치 |
|---|---|---|---|
| `password_reset` | 비밀번호 재설정 | ○ | `AccountService` 메일 |
| `password_changed` | 비밀번호 변경 안내 | ○ | `AccountService` 메일 |
| `welcome` | 가입 완료 안내 | ○ | **없음. 새로 만든다** |
| `comment_new` | 새 댓글·답글 | ○ | `NotificationService` 알림함 |
| `email_verify` | 이메일 인증 | ✗ | `AccountService` 메일 |
| `signup_attempt` | 가입 시도 안내 | ✗ | `AccountService` 메일 |
| `social_email_verify` | 소셜 로그인 이메일 확인 | ✗ | `SocialAuthService` 메일 |

아래 세 개는 이메일 채널 고유(수신자가 이메일로만 식별되거나 이메일 확인이 목적)라 알림톡·문자 열이 잠긴다. 그래도 `Notifier`를 지나게 바꾼다 — "알림은 전부 여기를 지난다"가 유지돼야 나중에 헷갈리지 않는다.

`comment_new`는 활동이 많은 사이트에서 발송량이 빠르게 는다. 설정 화면에서 그 사실을 알린다.

### 이벤트가 제공하는 변수

`Events`가 이벤트별로 고정 목록을 정의한다. 예를 들어 `password_reset`은 `사이트명`·`이름`·`링크`·`유효시간`이다. 화면은 이 목록을 그대로 보여준다.

### 채널별 본문

- **메일**: 지금 쓰는 제목·본문을 그대로 옮긴다.
- **문자**: 이벤트별 본문을 관리자가 직접 쓴다. 위 변수를 `#{이름}` 형태로 넣는다. 승인 절차가 없어 바로 켤 수 있다.
- **알림톡**: 켜진 승인 템플릿 중 하나를 고른다. 승인 템플릿의 변수명은 사이트마다 다르므로(`#{고객명}` / `#{이름}`) **매핑**이 필요하다. 템플릿을 고르면 본문에서 `#{...}`를 뽑아 목록을 만들고, 각 템플릿 변수에 코어 변수 중 무엇을 넣을지 고르게 한다. **매핑이 빠진 변수가 하나라도 있으면 그 이벤트의 알림톡을 켤 수 없다** — 켜자마자 전부 템플릿 불일치로 실패할 설정을 저장할 이유가 없다.
- **알림함**: 기존 `NotificationService` 동작 그대로다.

## 7. 회원 휴대폰번호

- `users.phone`에 하이픈을 뗀 숫자로 저장하고 화면에서만 넣어 보여준다. 정규화·검증은 `PhoneNumber` 한 곳에서만 한다.
- 입력받는 곳은 **가입**, **회원정보 수정**, **관리자 회원 수정** 세 곳이다.
- **가입 시 받을지는 "회원·글쓰기" 설정에서 `안 받음` / `선택` / `필수`로 고른다. 기본값은 `안 받음`이다.** 기존 사이트의 가입 흐름을 말없이 바꾸지 않기 위해서다.
- 본인확인은 하지 않는다. 형식만 검증한다.
- 관리자 회원 목록에서 휴대폰번호로 검색할 수 있게 한다. 발송 화면의 회원 선택이 그 검색을 쓴다.

## 8. 관리자 화면

### 설정 → 알림톡·문자 (`/admin/aligo`)

계정(사용자 ID·API 키), 발신번호, 발신프로필(**채널 불러오기** → `/profile/list/` 결과에서 선택), 채널별 발송 허용, 테스트 모드, **연결 확인**.

API 키는 메일 설정과 같이 저장 여부만 표시하고 값을 돌려주지 않는다. 빈 입력은 기존 키를 유지하고, 삭제 체크로만 지운다.

### 설정 → 알림 (`/admin/settings/notifications`)

행이 이벤트, 열이 메일·알림톡·문자·알림함인 표. 알림톡이나 문자를 켜면 그 행이 펼쳐지며 템플릿 선택·변수 매핑 또는 문자 본문 입력이 나온다.

### 운영 → 알림톡·문자 발송 (`/admin/messages/*`)

탭 세 개다.

- **발송** — 채널(알림톡·문자) 선택 → 알림톡이면 템플릿 선택, 문자면 본문 작성(남은 바이트와 SMS·LMS 판정을 실시간 표시) → 수신자 지정(회원 검색·체크 또는 번호 여러 줄 붙여넣기) → 변수값 입력 → 대체발송 여부 → **미리보기** → 발송. 번호 없는 회원을 고르면 제외하고 몇 명이 빠졌는지 알린다.
- **템플릿** — **가져오기**로 알리고 목록을 훑어 사본을 갱신한다. 승인·정상인 것만 켤 수 있고, 조건을 잃은 사본은 자동으로 꺼진다. 상세에서 본문과 버튼을 본다. 알림톡 전용 탭이다.
- **이력** — 작업 목록(요청 시각·채널·템플릿·건수·성공·실패·상태)과 상세(수신자별 결과와 사유). 결과 대기 중인 작업은 여기서 갱신된다.

## 9. 오류와 보안

- API 키는 화면·로그·예외 원문 어디에도 싣지 않는다. 알리고 응답 원문을 그대로 노출하지 않고 `ResultCodes`를 거친 사유만 보여준다.
- 이력 **목록**은 작업 단위라 수신번호가 아예 실리지 않는다(§8의 목록 항목과 같다). 번호는 **상세**에서만, 그것도 전부 그대로 보여준다.
- 수신번호는 이력에 **평문으로 보관한다.** 결과 조회와 재발송에 원본이 필요하고, 관리자만 보는 화면이기 때문이다(`feat/initalk`이 결제 요청의 번호를 암호화한 것과 다른 선택이며, 그쪽은 고객이 남긴 번호를 장기 보관하는 원장이라 성격이 다르다). 오래된 이력을 자동으로 지우는 보존 기간 설정은 이번 범위 밖이다.
- 모든 화면은 전역 관리자만 열 수 있다(`Acl::assertGlobalAdmin()`). 기존 CSRF를 그대로 탄다.
- 채널 발송 허용 스위치가 꺼져 있으면 화면과 확장 API 양쪽에서 발송을 거절한다.
- 자주 겪는 실패(잔여 건수 부족, 발신번호 미등록, 승인되지 않은 템플릿, 템플릿 불일치)는 사유와 함께 **해결 방법**을 적는다.

구현은 `superpowers:test-driven-development`에 따라 테스트를 먼저 쓴다. `AGENTS.md`대로 관련 테스트를 먼저 돌리고, 공통 코드·DB·라우팅을 건드리므로 전체 테스트도 돌린다.
