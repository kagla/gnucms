## 범위와 디자인

오늘의집의 검색·카테고리·프로모션·상품 목록 중심 탐색을 참고한 종합 쇼핑몰이다.
색상이나 스킨은 복제하지 않는다. GNUCMS 공통 레이아웃과 테마의 밝기 토큰을 바탕으로
독립적인 코럴 포인트, 뉴트럴 배경, 명확한 가격·할인율·배송 안내를 적용한다.
홈 프로모션은 카탈로그의 실제 상품 이미지를 사용한다. 상품 미등록·이미지 없음·품절도 처리한다.

모바일에서는 검색을 독립 행으로 배치하고 상품 목록은 두 열, 주문서는 한 열로 바꾼다.
상품 상세의 구매 버튼은 하단에 고정한다. 옵션과 추가 구성은 표준 폼으로 제출하므로
자바스크립트가 꺼져 있어도 동작한다. 자바스크립트는 금액 미리보기·이미지 전환·주문자 정보
복사·메뉴 닫기·오류 위치 안내만 보강한다. 운영 서버의 새 의존성 설치나 빌드는 없다.

## 책임과 경로

- `Commerce/Cart`: 장바구니 항목 추가·변경, 최신 카탈로그 검증, 가격·배송비 견적.
- `Commerce/Orders`: 주문 입력 검증·스냅샷 저장·재고 차감·멱등 접수, 조회 권한, 비회원 비밀번호
  확인·시도 제한, 상태 전이·재고 복원·처리 이력.
- `Web/CommerceController`: GNUCMS 세션 장바구니·바로 주문·주문서 토큰·조회 권한의 연결과 폼 응답.
- `Admin/OrderController`: 공통 관리자 권한 아래 목록 검색과 상태 변경.
- `bootstrap.php`: 고정 GET/POST 경로 등록. 공개 POST도 확장 런타임의 CSRF 검사를 거친다.
- 공개 경로: `/shop/cart`, `/shop/cart/add`(POST), `/shop/checkout`, `/shop/orders`,
  `/shop/order?number=...`, `/shop/order/cancel`(POST).
- 관리자 경로: `/admin/shop/orders`, `/admin/shop/orders/detail?id=...`.

기존 테마 재정의 우선순위와 내용 해시 자산 URL을 유지한다. 관리자 `admin/extension.php`는
공통 `admin/layout`과 `extensions.css`를 유지하며 모듈 CSS만 추가한다.

## 데이터와 업그레이드

모듈 스키마는 2판이다. 코어 `src/Db/Schema.php`와 제품 버전은 변경하지 않는다.
설치·갱신 POST에서 기존 멱등 DDL에 다음 세 테이블과 인덱스를 추가한다.

| 테이블 | 내용 |
|---|---|
| `yc_orders` | 무작위 접미사의 주문번호, 유일한 접수 키, 세션 소유 키, 회원 ID 또는 비회원 비밀번호 해시, 주문·배송 연락처, 상태, 상품·선불·착불 금액, 배송 계산 내역, 주문 안내, 운송장, 시각 |
| `yc_order_items` | 주문 ID, 원래 상품·옵션 ID, 본품/선택/추가 종류, 주문 당시 코드·이름·옵션명·이미지 파일명·단가·수량·금액 |
| `yc_order_history` | 주문 ID, 상태·처리자·관리자 메모·시각 |

외래키 대신 주문 서비스와 삭제 보호가 기존 확장 저장소 방식에 맞춰 관계를 보장한다.
주문이 있는 상품은 삭제하지 않고 비활성화한다. 접수·준비 중인 주문에 포함된 옵션은 삭제할 수
없다. 파일명만 보관하므로 상품 이미지가 삭제되면 주문 사진을 보존하는 아카이브 기능은 없다.
주문 상세는 이미지에 의존하지 않고 저장된 상품명·옵션명·가격으로 표시한다.
세 테이블을 `Schema::TABLES`에 등록해 확장 백업·복원 범위에 포함한다.

## 장바구니와 견적

장바구니 키는 `상품 ID:옵션 ID`, 옵션 없는 본품의 옵션 ID는 0이다. 세션에는 ID와 수량만
저장하며 가격 입력은 받지 않는다. 일반 장바구니와 바로 주문은 별도의 세션 항목이다.
기기 간 동기화와 세션 만료 후 복구는 제공하지 않는다.

견적은 상품·대표 분류의 활성 상태, 전화문의·품절, 옵션 소속·활성 상태, 재고, 수량을 검증한다.
본품 가격은 판매가에 선택옵션 차액을 더하고 추가옵션은 절대가를 쓴다. 본품 없이 추가옵션만
주문할 수 없다. 최소·최대수량은 상품별 본품 수량을 합산해 검사한다. 최대 100행·행당 9,999개다.

배송비는 기존의 다섯 유형을 계산한다. 기본배송 상품은 선불·착불별로 묶고, 조건부 무료 기준은
해당 묶음/상품의 옵션 포함 금액을 쓴다. 수량별 배송의 수량은 본품만 합산한다. 착불 금액은
별도로 표시하며 주문 금액에 더하지 않는다. 기본 배송비와 무료배송 기준 초기값은 0이다.
세부 공식과 운영 설정은 `docs/shop.md`에 정리한다.

## 주문 접수와 동시성

1. 주문서 GET에서 무작위 접수 토큰을 발급한다. 세션에 이용자·장바구니 종류·견적 지문을 연결한다.
   토큰은 최신 12개를 유지해 여러 탭을 지원한다.
2. POST는 CSRF, 토큰·이용자 일치, 필수 연락처·우편번호·동의·비회원 비밀번호를 검증한다.
   일반 이용자의 주문 접수 시도는 10분에 20회로 제한한다.
3. 주문 서비스는 상품 ID 순으로 상품 행을 잠근 뒤 최신 견적을 계산한다. 가격·배송비·수량·옵션·
   안내가 바뀌었다면 다시 검토하게 한다. 브라우저 금액은 신뢰하지 않는다.
4. 한 트랜잭션에서 주문·항목·이력과 재고 차감을 저장한다. 조건부 UPDATE로 재고 음수를 막는다.
   하나라도 실패하면 전체를 롤백한다. 주문 시 상품 버전을 증가시켜 이전 상품 수정 폼을 무효화한다.
5. 유일한 접수 키와 세션 소유 키로 같은 요청의 재전송에 최초 주문을 반환한다. 성공 후 해당
   장바구니만 비우고 PRG로 주문 상세에 이동한다. 기존 장바구니는 바로 주문에 영향받지 않는다.

관리자의 일괄 편집·재고 폼은 `original_stock`으로 조회 당시 재고를 제출한다. 서버는 잠근 뒤
현재 재고와 비교하여 주문으로 차감된 재고를 오래된 폼이 덮어쓰지 못하게 한다. 옵션 재고는
MySQL의 현재 읽기(`FOR UPDATE`)를 사용해 반복 읽기 스냅샷에도 최신 재고를 확인한다.

## 조회·취소·운영

회원은 자신의 주문만 조회한다. 관리자는 관리자 경로에서 타인의 주문을 처리하며 공개 경로에서
관리자라는 이유로 다른 회원 주문을 열 수 없다. 비회원은 주문 접수 직후 같은 세션 또는 주문번호·
이메일·비밀번호로 인증한 세션에서 조회한다. 비밀번호는 해시만 저장하고 폼에 재출력하지 않는다.
비회원 조회는 IP별 10분에 5회 실패 시 잠그며 존재하지 않는 주문도 같은 오류를 반환한다.
주문 관련 응답은 `Cache-Control: no-store`와 검색 제외 메타 태그를 사용한다.

상태는 `pending → confirmed → shipped → completed`다. 접수/준비 상태에서 전체 취소할 수 있고
구매자의 직접 취소는 접수 상태에 한한다. 배송 중으로 전환할 때 택배사·운송장 번호가 필수다.
상태를 조건부 UPDATE해 반복 취소나 오래된 상태 변경을 거절한다. 취소는 재고를 한 번 복원하고
원장에 기록한다. 배송 완료 시 본품의 판매수량을 올린다. 관리자 메모는 구매자에게 노출하지 않는다.

주문 접수는 온라인 결제가 아니다. PG·환불·부분 취소·자동 입금 확인·자동 만료·주문 알림 발송은
추후 단계다. 적립금도 지급하지 않는다. 운영자는 접수 주문을 확인해 결제·배송을 안내하고
미진행 주문을 취소해야 한다. 기존 결제·메시징 전용 브랜치의 코드는 가져오지 않는다.

## 검증

기존 카탈로그·공개·관리자 회귀 테스트와 `CommerceTest`, `YoungCartCommerceTest`에서 SQLite와
MySQL/MariaDB를 함께 검증한다. 설치/1판 갱신, 옵션 차액·추가 구성, 배송 묶음·무료 기준·착불,
가격 조작·변경, 품절, 주문 스냅샷, 중복 제출, 회원 간 접근 분리, 비회원 비밀번호·시도 제한,
CSRF, 상태 전이, 취소 복원, 오래된 재고 폼, 하위 경로 설치를 포함한다.
별도 임시 DB·업로드를 사용하는 브라우저 확인으로 실제 구매 흐름, 화면 폭·다크 모드·관리자
화면을 점검한다. 데모 데이터와 브라우저 도구는 배포본과 저장소에 포함하지 않는다.

검증 결과: SQLite·MariaDB 전체 1,143개 테스트 / 6,506개 단언 통과. 브라우저에서는 360·390·768·
1,280px의 공개 화면 20개 조합에서 가로 넘침이 없음을 확인했고, 자바스크립트를 끈 장바구니·
주문서도 확인했다. 재고 1개에 독립 프로세스 두 개가 동시에 주문했을 때 한 건만 접수되고
다른 한 건은 422 재고 부족으로 거절됐다.
