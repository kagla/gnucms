일별 CSV는 HTTP 200, `text/csv`로 내려왔고 요약행 `3100,2000,1100,1000,100,0,0,3,3`과 두 상품코드를 포함했다. 월별 화면도 조회했으며 9월 전체 31건·결제 76,060원·환불 13,600원·순매출 62,460원이었다. 월별 값에는 기존 사이트 주문이 포함되므로 이번 테스트만의 합계가 아니다.

토스 테스트 주문의 정산 상태는 처음 `정산 없음`이었다. **실제 PG 정산 자료가 없어**, 표준 CSV 형식의 **모의** 결제 +1,100원과 환불 −1,100원 두 행을 테스트 거래에 연결했다. 첫 행만 가져오자 `금액 불일치`, 두 번째 행까지 가져오자 `일치`(주문 순액 0원, 정산 합계 0원, 2건)로 바뀌었다. 같은 행 재가져오기는 0건 추가·1건 중복 건너뛰기, 같은 거래 키의 다른 금액은 오류로 처리됐다. 유효하지 않은 `provider` 값도 가져오기를 거절했다. ## 자동 검증

자동 결제 검사는 다섯 PG 어댑터의 주문서·콜백·모의 승인/취소 경로를 포함하지만, PG 외부의 실제 샌드박스 인증을 대신하지 않는다.

첫 브라우저 실패는 테스트 픽스처가 현행 상품 템플릿에 필요한 `copy_source`, 분류 `slug`, 수정 상품의 `id`·`name` 값을 제공하지 않아 PHP 경고 문구가 HTML에 삽입된 결과였다. 경고가 가로 길이를 늘려 390px 검사에 걸렸다. 실제 사이트의 상품 등록·수정 화면은 390px 밝은·어두운 테마 모두 문서 너비 390px으로 확인했고, 실제 관리자 화면에서 선택옵션 3개 조합을 만들어도 넘침이 없었다. `ShopAdminOptionsFixture.php`의 데이터를 보완하고 `ShopAdminOptions.cjs`에 경고 없는 렌더링 검사를 추가했다. 제품 코드는 바꾸지 않았다.

## 남은 범위와 유지 데이터

- 이번 실사이트에서 외부 PG까지 완료한 것은 토스 1종이다. 이니시스·KCP REST·KCP 기존 방식·나이스페이의 외부 카드 인증과 취소, 실제 택배사 인계, 실제 은행 입출금, 실제 PG 정산 지급은 확인하지 않았다.
- 이미지 업로드, 옵션의 모든 조합, 동시 주문 재고 경합, 다수 고객 권한 교차 검증까지 모든 가능한 입력 조합을 전수 실행한 것은 아니다. 이 보고서의 통과는 위에 적힌 시나리오와 자동 검사의 범위에 한한다.
- 테스트 분류 ID 9, 상품 ID 16·17, 주문 ID 44~47, 테스트 토스 결제·환불과 **모의** 정산 CSV 2행은 추적을 위해 사이트에 남겼다. 임시 하위 분류 ID 10은 삭제했다. 실제 송금·배송은 발생하지 않았다.
- 로컬 자동 검사에 만든 전용 DB와 DB 사용자 계정은 검증 후 삭제했고, 둘 다 존재하지 않음을 확인했다. 임시 관리자 인증 환경 파일·서명된 주문 링크가 담긴 상태 파일·CSV 파일도 삭제했다. Chrome/Puppeteer의 기존 `/tmp/gnucms-ai-browser/node_modules` 설치는 유지했다.
