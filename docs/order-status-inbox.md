# 주문 상태의 사이트 내 알림

> 과거 계획·작업 기록입니다. 작성 당시의 제안·검증 결과는 보존하며 현재 기능 제공을 보장하지 않습니다. 현재 지원 범위는 [공개 매뉴얼](https://gnucms.com/manual/support)과 [지원 범위 문서](https://github.com/kagla/gnucms/blob/main/docs/supported-features.md)를 따릅니다. 백업·확장·쇼핑몰은 현재 코어에 구현되어 있으며 자동 복원·자동 DB 백업은 제공하지 않습니다.

관리자가 상품 준비(`confirmed`), 배송 중(`shipped`), 배송 완료(`completed`)로 실제 상태를 변경하면 활성 주문 회원에게 사이트 내 알림을 한 건 저장한다. 관리자 주문 목록·상세·배송 CSV 모두 `Orders::transition()`을 사용한다. 현재 상태와 요청한 이전 상태가 일치하지 않거나 허용되지 않는 전이면 알림을 만들지 않는다. 되돌린 뒤 다시 정상적으로 진행한 상태 변경은 새 알림이다.

알림은 상태 변경 및 주문 처리 이력과 같은 트랜잭션에서 기록한다. CSV의 바깥 트랜잭션이 취소되면 앞서 기록한 알림도 취소된다. 알림 저장 자체가 실패해도 주문 상태만 먼저 바뀌는 상황을 허용하지 않는다. 외부 발송기·메일·알리고는 호출하지 않으며 기존 이벤트별 발송 규칙에는 주문 이벤트를 추가하지 않는다.

댓글과 주문 알림을 같은 알림함과 미읽음 수에 포함한다. 목록 열기는 읽음 처리하지 않는다. 주문 알림 클릭은 알림 수신자와 현재 주문 소유자를 둘 다 확인한 후 읽음으로 바꾸고 `/shop/order?number=...`로 이동한다. 기존 주문 상세 경로가 본인 확인 및 표준 `ref` 주소 이동을 수행한다. 전체 읽음의 CSRF 검사와 종 숫자의 페이지 요청 시 갱신 방식은 유지한다.

## DB 및 배포

- DB 스키마 48 → 49. 신규 설치는 `notifications.order_id BIGINT NULL` 및 nullable `post_id`를 만든다.
- 기존 설치는 빠진 `order_id`만 추가하고, `post_id`가 NOT NULL일 때만 nullable로 변경한다. 기존 댓글 행을 수정하거나 과거 주문 알림을 생성하지 않는다. 반복 실행해도 안전하다.
- 운영 배포 전에 현재 관련 파일과 변경 대상 알림 테이블·판 도장의 접근 제한 백업을 준비한다. 이번 변경은 다른 테이블·설정을 바꾸지 않는다. 런타임 백업에는 개인정보가 포함되므로 다운로드·공유·로그 출력하지 않는다. 기존 SchemaUpgrader는 자동 DB 백업을 실제로 만들지 않으므로 운영 요청의 자동 백업을 가정하지 않는다.
- 실제 운영 DB의 ALTER 권한을 확인하고, 가능하면 트래픽을 잠시 멈춘 뒤 확장 DDL을 먼저 적용한다. 오래된 코드도 새 nullable 컬럼을 무시할 수 있다. 새 코드를 전부 교체한 뒤 공식 마이그레이션으로 도장을 갱신한다. 운영 DB에서 테스트를 실행하지 않는다.
- 배포 시 의존성 설치·빌드를 하지 않는다. 기존 vendor와 정적 자산을 사용한다. version.txt 및 무관한 운영 변경을 덮어쓰지 않는다.
- 롤백은 관련 코드 백업을 복원하고 신규 주문 알림만 별도 보관 후 알림함에서 제거해야 한다. 이전 UI는 주문 종류를 이해하지 못한다. 기존 댓글 알림은 보존한다. 확장 컬럼은 남겨도 이전 코드가 사용할 수 있으며, nullable 주문 행이 남은 채 post_id를 NOT NULL로 되돌려서는 안 된다. DB 전체 복원은 배포 이후 정상 운영 데이터도 지우므로 별도 판단 없이 실행하지 않는다.

## 검증

`tests/Web/OrderNotificationTest.php`는 세 상태·중복 요청·종 합산·개별/전체 읽음·외부 메일 미발송·관리자 목록/상세·CSV 성공/롤백·타인 접근/잘못된 대상·기존 댓글 마이그레이션을 검증한다. 기존 댓글 알림 및 쇼핑몰 주문·배송·스키마 회귀 테스트와 함께 전용 MySQL DB에서 실행한다.
