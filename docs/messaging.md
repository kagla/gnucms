# 알림톡·문자 발송 (알리고)

GNUCMS 코어는 [알리고](https://smartsms.aligo.in) 계정으로 카카오 **알림톡**과
**문자(SMS·LMS)** 를 보내는 기능을 내장한다. 관리자가 화면에서 직접 보낼 수 있고,
확장(모듈·플러그인)은 `$app->aligo()->send()` 하나로 같은 엔진을 쓸 수 있다.

코어 자동 알림은 공통 발송 설정과 이벤트별 메일·문자 선택을 따른다. 이메일 인증 등 이메일 전용 이벤트는 전화 채널을 지원하지 않는다. 알림함을 지원하는 이벤트만 필수 기록하며, 이메일 인증과 로그인 전 비밀번호 재설정에는 알림함을 만들지 않는다. 자세한 운영 절차는 [공개 매뉴얼](https://gnucms.com/manual/messages/channels)과 §10을 따른다.

## 1. 알리고 계정 준비

발송을 켜기 전에 알리고 쪽에서 먼저 해 둘 것이 있다.

- **발신번호 사전 등록**: 문자를 보내려는 전화번호를 알리고 관리 화면에 미리 등록해
  둬야 한다. 등록하지 않은 번호로는 발송이 거절된다.
- **카카오채널 연결과 알림톡 신청**: 알림톡을 쓰려면 카카오채널을 만들어 알리고에
  연결하고 알림톡 서비스를 신청해야 한다. GNUCMS는 카카오채널을 새로 만들지 않는다 —
  이미 연결된 발신프로필 중에서 고를 뿐이다.
- **템플릿 검수**: 알림톡 본문(템플릿)은 카카오 검수를 거쳐야 승인된다. 심사 일정은 알리고에서 확인한다. **GNUCMS는 템플릿을 작성·수정·삭제·검수 요청하지 않는다.** 템플릿은 알리고
  관리 화면에서 만들고 검수를 신청한 뒤, GNUCMS에서는 승인된 결과만 가져온다.

계정이 준비되면 사용자 ID와 API 키를 발급받는다.

## 2. 설정 화면 (설정 → 알림·발송 / 알림별 발송 규칙)

사이트 설정의 **알림·발송**(`/admin/settings/messaging`)에서 메일 사용 안 함·서버 기본 메일·SMTP와 알림톡·문자 네 가지 방식(사용 안 함·문자만·알림톡 후 문자·알림톡만)을 관리한다. SMTP를 선택하면 입력란을 펼치고 저장 버튼으로 적용한다. 전화 방식은 선택 즉시 두 채널 상태를 함께 저장한다. 실제 자동 발송에는 알림별 메일·문자 선택도 함께 적용한다. 필수 알림함은 개별 선택·배지로 표시하지 않는다.
SMTP 메일 서비스는 Gmail·네이버 메일·카카오 메일·다음 메일·직접 설정 순서로 제공한다. 카카오 메일을 선택하면 `smtp.kakao.com`·465·SSL/TLS를 화면과 서버 저장에서 적용한다. 카카오계정의 2단계 인증과 앱 비밀번호를 설정하고 카카오메일 설정 → IMAP/POP3 → IMAP에서 IMAP/SMTP 사용을 켠다. SMTP 사용자 이름에는 `@kakao.com` 앞의 아이디를, 발신 이메일에는 해당 아이디의 전체 카카오메일 주소를 입력한다. 일반 로그인 비밀번호 대신 앱 비밀번호를 사용한다.
메일 설정과 테스트 메일 발송은 알림·발송 화면에서 함께 관리한다. 테스트 메일은 저장된 설정으로 보내므로 변경한 설정을 먼저 저장한 뒤 수신 이메일을 입력한다. 성공·검증 오류·발송 오류도 같은 화면에 표시한다. 테스트 메일 본문에는 `app.url`의 도메인, 서버 요청 환경의 `SERVER_ADDR`를 검증한 웹서버 IP, 사이트 시간대의 발송 시각과 발송 방식(SMTP는 서버명 포함)을 표시한다. IP를 얻을 수 없으면 확인할 수 없음을 표시하며 방문자 IP나 도메인 DNS 결과로 대체하지 않는다. 웹서버 IP가 SMTP 발송 서버 IP와 다를 수 있음을 안내한다. 이 발송 환경 정보는 테스트 메일에만 포함한다. 메일을 사용하지 않는 상태에서는 테스트 발송 폼 대신 안내를 표시한다. 기존 `/admin/mail` 주소는 통합 화면으로 이동하고 저장·테스트 POST 경로는 호환한다. SMTP 암호화·검증·빈 비밀번호 보존 규칙을 유지한다. 알리고 계정·발신번호·카카오채널 연결은 `/admin/aligo`에서 관리한다.
문자·알림톡 설정 화면 상단의 **알리고 사이트로 이동** 버튼은 알리고 공식 사이트(`https://smartsms.aligo.in/`)를 새 창으로 연다.
알림별 채널 선택과 문구 편집은 `/admin/settings/notifications`의 별도 **알림별 발송 규칙** 탭에서 관리한다.
통합 주소 `/admin/settings/messaging`의 과거 메일 저장·테스트 결과 쿼리는 같은 화면에서 표시한다. 알리고 저장 결과와 알림별 발송 규칙 저장 결과 쿼리는 각각의 상세 화면으로 이동한다.
각 영역은 따로 저장하므로 한 영역의 설정이 다른 영역을 덮어쓰지 않는다.
문자·알림톡 화면에서도 공통 계정과 알림톡 전용 설정은 각각 별도 폼으로 저장한다.
문자·알림톡 화면은 위에서부터
**전체 채널 사용 설정으로 이동**, **공통 · 알리고 계정**(두 채널이 함께 쓰는
값), **알림톡 (카카오)**(알림톡에만 쓰는 값), **문자 (SMS·LMS)**(따로 입력할 값이 없다는
안내) 순이다.

- **알리고 사용자 ID**: 알림톡·문자 양쪽 인증에 함께 쓴다. 화면에는 괄호를 달지
  않는다 — 같은 값인데도 문자 API 는 `user_id`, 알림톡 API 는 `userid` 로 실어
  보내므로(`SmsApi::call()`, `AlimtalkApi::call()`), 둘 중 하나만 적으면 나머지
  한쪽에서 틀린 이름이 된다.
- **API 키**: 알리고에서 발급받은 키 하나로 알림톡·문자 양쪽을 인증한다. 알림톡용
  키는 따로 없다 — 문자 API 스펙(`admin/api/spec.html`)의 `key`와 알림톡 API
  스펙(`alimapi.html`)의 `apikey`는 둘 다 "인증용 API Key"이고 같은 값이다. 저장은
  암호문으로 하고, 화면 HTML 에는 싣지 않는다(소스 보기에 나오면 안 된다). 눈 아이콘을
  누르면 CSRF 를 확인한 POST(`/admin/aligo/key`)로 받아 칸에 채우고, 그 뒤 칸을 비우고
  저장하면 지워진다. 불러오지 않은 빈 칸은 기존 키를 유지하며, 따로 삭제 체크는 없다.
- **발신번호**: 알리고에 사전 등록한 번호와 정확히 같아야 한다. 알림톡·문자
  모두 이 번호로 나간다.
- **발신프로필키 (Senderkey)**: 알림톡 전용. 카카오채널 하나를 가리키는 값이고, 직접
  입력하거나 **채널 불러오기**로 알리고에 등록된 채널 목록을 불러와 고를 수 있다.
  화면에서 영문 이름을 괄호에 다는 유일한 칸이다 — 알리고가 실제로 Senderkey 라고
  부르고, 두 알림톡 호출 모두 `senderkey` 로 보낸다.
- **카카오채널명**: 화면에서 알아보기 위한 이름일 뿐 발송에는 쓰이지 않는다.
- **전체 채널 사용 설정**: 공통 전화 방식으로 두 채널을 함께 정한다. 사용 안 함은 둘 다 끄고 문자만·알림톡 후 문자·알림톡만은 해당 조합을 저장한다. 상태와 예약 취소 결과를 확인하며, 관리자 직접 발송과 확장 공개 API에도 같은 전역 허용 검사를 적용한다.
- **테스트 모드**: 켜면 알리고 API를 실제로 호출하되 과금·실제 발송 없이 파라미터
  검증까지만 한다. 이 모드로 보낸 작업은 이력에 **테스트**로 표시된다.
- **연결 확인**: 저장한 키로 알림톡 잔여 건수(`heartinfo`)와 문자 SMS·LMS 잔여
  건수(`remain`)를 함께 조회해 한 줄로 보여준다. 알림톡과 문자는 알리고 안에서도
  별개로 신청하는 서비스라서, 계정에 따라 한쪽만 신청되어 있을 수 있다. 그래서 두
  조회는 서로 독립적으로 실패를 허용한다 — 한쪽이 실패해도 나머지 한쪽은 알아낸
  그대로 보여준다.

## 3. 알림톡과 문자의 차이

알리고는 **알림톡 API**(`kakaoapi.aligo.in`)와 **문자 API**(`apis.aligo.in`)를 완전히
분리된 두 서비스로 제공한다. 호스트, 인증 파라미터 이름과 응답 판정 방식이 다르다. API 요청의 본문·제목은 두 채널 모두 UTF-8이다.

| | 알림톡 | 문자(SMS·LMS) |
|---|---|---|
| 호스트 | `kakaoapi.aligo.in` | `apis.aligo.in` |
| 인증 파라미터 | `apikey` / `userid` | `key` / `user_id` |
| 성공 판정 | 응답 `code === '0'` | 응답 `result_code === '1'` |
| API 요청 인코딩 | UTF-8 | UTF-8 (길이·지원 글자 검사는 EUC-KR) |
| 본문 | 승인된 템플릿 그대로만 | 관리자가 직접 작성 |

문자가 알림톡보다 더 많이 쓰일 것으로 보고 설계했다 — 알림톡은 템플릿 승인을
기다려야 하고 승인된 문구를 벗어날 수 없지만, 문자는 검수 절차 없이 바로 쓸 수
있다. 그래서 문자는 알림톡의 대체 수단이 아니라 **동등한 1급 채널**이다.

문자 API는 수신자별 변수 치환을 지원하는 `/send_mass/`만 쓴다. 최대 인원 제한이
1,000명인 `/send/`가 있지만 그쪽은 수신자 전원에게 같은 본문만 보낼 수 있어 쓰지
않는다.

## 4. EUC-KR 제약

문자(SMS·LMS)는 EUC-KR로 인코딩해 바이트 수를 잰다. **UTF-8이 아니라 EUC-KR 바이트
기준이므로 한글 한 글자는 2바이트다**(UTF-8이었다면 3바이트).

- **SMS**: 90바이트까지. 넘으면 자동으로 **LMS**로 전환된다.
- **LMS**: 2,000바이트까지. 제목은 44바이트(한글 기준 22자)까지.
- EUC-KR로 옮길 수 없는 글자(이모지 등)가 본문에 하나라도 있으면, 보내기 전에
  **거절하고 어느 글자가 문제인지 알린다.** 깨진 문자로 바꿔서 내보내지 않는다.

알림톡 본문은 이 제약과 무관하다 — UTF-8 그대로 보낸다. EUC-KR 규칙은 알림톡이
실패했을 때의 **대체문자(failover)** 본문에만 적용된다.

## 5. 템플릿 (알림톡·문자 발송 → 템플릿)

GNUCMS는 알림톡 템플릿을 직접 작성하지 않는다. **가져오기**를 누르면 알리고에
등록된 템플릿 목록을 읽어 읽기 전용 사본으로 저장하거나 갱신한다.

- 별도 켜기·끄기나 로컬 승인 버튼은 없다. 카카오 검수 승인(`insp_status === 'APR'`)과 정상·대기 상태(`A`·`R`)의 현재 발신프로필 템플릿을 선택한다. 미승인·중단·목록에서 사라진 템플릿은 발송에서 제외한다.
- 상태 대기와 카카오 검수 대기를 구분한다. 화면에서 상태·검수 상태와 본문·버튼을 모달로 확인한다.
- 가져오기에서 승인 상실·중단·누락을 확인하면 관련 예약을 취소 시도한다. 응답 전체가 불명확한 조회 실패에서는 기존 사본을 임의로 비우지 않는다.
- 발송 화면 링크는 템플릿이 선택된 입력 화면으로만 연결한다. 실제 발송은 수신자·변수와 미리보기를 확인한 뒤 별도로 실행한다.

## 6. 발송 (운영 → 알림톡·문자 발송 → 발송 탭)

관리자는 채널(알림톡·문자)을 고르고, 알림톡이면 승인된 사용 가능 템플릿을, 문자면 본문을 직접
쓴다. 수신자는 회원 검색·선택이나 번호 여러 줄 붙여넣기로 지정한다. 화면은 **먼저
미리보기로 받는 사람 수·제외 인원과 첫 번째 수신자에게 나갈 본문을 확인한 뒤에만
발송** 버튼을 보여준다 — 문자라면 실제 바이트 수와 SMS·LMS 판정도 미리보기에
함께 나온다.

회원 선택 목록에는 **정상 상태(`active`)인 회원만** 나온다. 차단되었거나 탈퇴한
회원은 발송 대상 선택에서부터 제외된다.

발송은 채널별 허용 스위치가 꺼져 있으면 화면에서도, 확장 API에서도 거절된다. 한 번
쌓인 발송 작업은 **재시도하지 않는다** — 500명씩 나눠 부른 호출 가운데 응답이
끝내 오지 않은 묶음은 그대로 `failed`로 남는다. 같은 요청을 다시 알리고에 보내면
중복 발송이 되기 때문이다(조회만 재시도한다).

### 확장에서 일괄 발송하기

```php
$app->aligo()->send([
    'channel'  => 'sms',            // 'at' | 'sms' ('lms'는 본문 길이로 자동 판정)
    'body'     => '#{이름}님, 주문 #{주문번호}이 발송되었습니다.',
    'title'    => '배송 안내',       // LMS로 넘어갈 때만 쓰인다
    'tpl_code' => null,             // 알림톡이면 필수 — 승인된 사용 가능 템플릿 코드
    'failover' => false,            // 알림톡 실패 시 문자로 대체발송할지
    'recipients' => [
        ['phone' => '01012345678', 'name' => '홍길동', 'vars' => ['이름' => '홍길동', '주문번호' => 'A-1001']],
        ['phone' => '01098765432', 'name' => '김철수', 'vars' => ['이름' => '김철수', '주문번호' => 'A-1002']],
    ],
]); // int, message_jobs.id 를 돌려준다
```

관리자 화면과 완전히 같은 경로(`Dispatch::send()`)를 지난다 — 채널 허용 스위치,
번호 정규화·중복 제거, 변수 치환 검증(값이 빠진 변수가 하나라도 있으면 작업 전체를
만들지 않고 거절), 500명 분할 호출을 전부 그대로 적용받는다. 자세한 규칙은
[`docs/superpowers/specs/2026-09-17-aligo-messaging-design.md`](superpowers/specs/2026-09-17-aligo-messaging-design.md)
§4를 참고한다.

`send()`가 돌려주는 정수는 `message_jobs.id`다. 그 작업의 `message_jobs.status`는
`scheduled`(예약을 걸어 두고 발송 시각을 기다리는 중) · `sending`(아직 결과를
기다리는 중) · `sent`(전원 전달 성공) · `failed`(전원 실패) · `partial`(일부만 발송 —
확인된 실패가 있거나 일부가 취소됐거나 둘 다) · `unknown`(결과를 알아내지 못하고
포기한 건이 남음) · `cancelled`(예약을 취소함) 일곱 값 중 하나로 정리된다.
`scheduled`는 수신자 결과를 세어서 나오는 값이 아니라 예약이라는 사실 자체이므로
수신자 결과 집계 규칙(아래 §8)과 별도로 다뤄진다. 수신자별
`message_recipients.status`는 `queued`·`accepted`·`sent`·`failed`·`unknown`·
`cancelled`(취소된 묶음에 속한 수신자)다(아래 §8).

작업의 `status`·`success`·`failure`·`cancelled`는 **두 단계로 정해진다.** 발송 직후에는 알리고가
돌려준 접수 건수(`scnt`·`fcnt`)가 들어가고 상태는 `sending`이다 — 접수는 전달이
아니므로 이 시점에 `sent`(전원 성공)라고 적지 않는다. 그 뒤 결과를 조회할 때마다
수신자 행에서 다시 세어 전달 성공·실패 건수로 바뀐다. 그래서 목록의 성공·실패
숫자와 상세의 수신자별 결과는 항상 같은 말을 한다. 아직 결과를 기다리는 수신자가
한 명이라도 남아 있으면 작업은 최종 상태로 넘어가지 않는다. 대체발송을 켠
알림톡은 대체문자 결과가 최종 답이다 — 알림톡이 실패해도 대체문자가 도착했으면
그 수신자는 작업 집계에서 성공이다.

취소된 수신자는 성공도 실패도 대기도 아니다 — 그 사람은 메시지를 받지 못했고 앞으로도
받지 못한다(관리자가 그렇게 정했다). 그래서 `message_jobs.cancelled`라는 자기 칸을
갖고 이력 목록에도 **취소** 열로 나온다:
`총 = 성공 + 실패 + 취소 + 아직 기다리는 중 + 불명확`(7일이 지나 조회를 포기한 건)
이 언제나 맞아떨어져야 관리자가 "그럼 나머지는 어디 갔나"를 묻지 않는다. 취소가 하나라도
있는 작업은 절대 `sent`(전원 전달 성공)가 되지 않는다 — 전원이 취소됐으면 `cancelled`,
일부만 취소됐으면 `partial`이다.

## 7. 예약 발송과 취소

발송 탭·확장 모두 발송 시각(`scheduled_at`)을 함께 줄 수 있다. 비우면 즉시 발송,
채우면 예약이다. 예약과 즉시 발송은 같은 경로(`Dispatch::send()`)를 지나므로
채널 허용 스위치, 번호 정규화, 변수 치환 검증, 500명 분할 같은 규칙은 그대로
적용된다 — 예약이라고 해서 검사가 약해지지 않는다.

### 예약은 거는 순간 알리고로 넘어간다

**예약을 걸면 그 즉시 메시지가 알리고에 접수된다.** 발송 시각이 됐을 때 GNUCMS가
다시 알리고를 부르는 것이 아니라, 알리고가 접수해 둔 요청을 스스로 그 시각에
내보낸다. **채널 발송 허용 스위치와(알림톡이라면) 템플릿의 승인 상태는 이 접수
시점에 한 번만 확인**되고, 그 뒤로는 다시 검사하지 않는다. 접수된 다음부터
GNUCMS가 그 예약에 손댈 수 있는 유일한 방법은 취소 호출뿐이다 — 그래서 아래
규칙은 전부 "이미 알리고 손에 있는 것을 어떻게 정직하게 다루는가"에서 나온다.
채널을 끄거나 템플릿이 승인을 잃어도 이미 접수된 예약이 저절로 멈추지 않는
이유이기도 하다 — 그 대신 GNUCMS가 그 순간 취소를 시도한다(아래 참고).

### 예약 시각의 범위

예약 시각은 **지금부터 10분 뒤 이후, 30일 이내**여야 한다. 하한 10분은 알리고
문자 API 자체가 요구하는 값이다 — 알림톡 쪽에는 문서화된 하한이 없지만, 설명을
하나로 두기 위해 같은 규칙을 그대로 적용한다. 상한 30일은 GNUCMS가 정한 값이다 —
기한 없는 예약은 아무도 기억하지 못하는 발송이 되기 때문이다. 범위를 벗어난
시각은 작업 자체를 만들지 않고 그 자리에서 거절한다(발송 탭이면 다시 그려진
입력칸에, 확장이면 `DomainError`로).

### 시간대: 입력은 오프셋 유무로 갈리고, 저장은 UTC, 알리고에는 다시 한국 시각

예약 시각을 다루는 지점들의 기준은 규칙 하나로 정해진다(모두
`GnuCms\Aligo\SendTime` 한 클래스 안에서만 정해진다).

- **`scheduled_at`에 오프셋(예: `+09:00`, `Z`)이 붙어 있으면 그 오프셋 그대로
  절대 시각을 읽는다.** 오프셋이 없으면 사이트가 실제로 쓰는 시간대, 즉 한국
  표준시(KST, UTC+9, 서머타임 없음) 벽시계로 읽는다. 발송 탭의 시각 입력칸
  (datetime-local)은 오프셋을 낼 수 없으므로 언제나 오프셋 없이 KST 로 읽힌다 —
  이 화면의 다른 모든 시각과 같은 기준이다.
- **저장은 UTC다.** `message_jobs.scheduled_at`에는 `Clock`과 같은 규칙으로 UTC
  `Y-m-d H:i:s` 문자열이 들어간다.
- **알리고에 보낼 때는 다시 한국 시각으로 바꾼다.** 알림톡은 `senddate` 한 칸
  (`YYYYMMDDHHMMSS`)에, 문자는 `rdate`(`YYYYMMDD`)·`rtime`(`HHII`) 두 칸에 나눠
  담는다.

**확장이 `$app->aligo()->send(['scheduled_at' => …])`로 예약할 때도 화면과 같은
규칙 하나를 쓴다.** `Dispatch::send()`가 부르는 `SendTime::parse()`는 화면이 쓰는
것과 같은 메서드다 — 확장이 한국 시각 벽시계 값을 오프셋 없이 그대로 넘기면
관리자가 입력한 것과 똑같이 KST 로 읽혀 제 시각에 예약된다. 이미 다른 시간대
기준으로 계산해 둔 절대 시각을 넘기고 싶다면 그 값에 오프셋을 붙이면 된다 —
예를 들어 `2026-09-20T14:00:00+09:00`은 오프셋이 없는 `2026-09-20T14:00:00`과
같은 순간을 가리키고, `2026-09-20T14:00:00+00:00`은 9시간 뒤의 다른 순간을
가리킨다.

### 취소는 발송 5분 전까지, 500명이 넘으면 부분 취소가 있을 수 있다

예약은 **발송 5분 전까지** 취소할 수 있다 — 이것은 알리고 쪽 제한이며, GNUCMS가
따로 시각을 계산해 그보다 먼저 취소를 막지 않는다. 이력 상세 화면은 작업이
`scheduled` 상태인 동안 항상 취소 버튼을 보여주고, 실제로 취소되는지는 알리고에
요청을 보내 본 뒤에야 갈린다.

500명이 넘는 작업은 500명 단위 묶음마다 알리고에 따로 접수(묶음마다 다른 `mid`)
되므로, 취소도 묶음 단위로 따로 이뤄진다. **한 작업의 취소가 일부 묶음만 성공하고
나머지는 실패할 수 있다.** 화면은 이 사실을 뭉개지 않는다 — 몇 개를 취소했고 몇 개를
취소하지 못했는지 숫자 그대로 보여주고, 하나라도 남았으면 안내는 성공(초록)이 아니라
주의(노랑)로 나온다. 하나라도 취소하지 못한 채 남아 있으면 작업 상태도 `cancelled`로
바뀌지 않고 `scheduled`로 남는다(아직 나갈 몫이 있다는 뜻이다).

**왜 취소하지 못했는지는 안내 문장이 단정하지 않는다.** 시한(발송 5분 전)을 지나서일
수도 있지만, 알리고에 닿지 못했거나 API 키가 취소됐거나 서버 IP 가 등록돼 있지 않아도
똑같이 실패한다 — 알림톡 쪽에는 시한 초과를 가리키는 응답 코드 자체가 없어 가려낼
방법조차 없다. 틀린 사유는 침묵보다 나쁘다: "시한이 지났습니다"는 다시 시도하지 말라는
지시인데, 일시적인 통신 실패였다면 다시 눌렀을 때 실제로 취소됐을 것이다. 그래서 화면은
개수만 말하고, 알리고가 실제로 돌려준 사유는 그 묶음의 수신자 행에 적혀 **이력 상세의
"사유" 칸**에 그대로 보인다. 취소 버튼은 그대로 남아 있어 다시 누를 수 있고, 이미
취소된 묶음은 다시 부르지 않으므로 다시 눌러도 안전하다.

### 채널을 끄거나 템플릿이 승인을 잃으면

설정 화면에서 알림톡·문자 채널을 끄거나, 템플릿 탭에서 **가져오기**를 눌러 이미
사용 가능했던 알림톡 템플릿이 승인을 잃거나 중단·누락되어 발송에서 제외되면, 그 채널·
템플릿에 걸려 있던 예약을 GNUCMS가 **자동으로 취소 시도**한다(다른 채널·다른
템플릿의 예약은 손대지 않는다). 이 취소도 앞서와 같이 부분적으로만 성공할 수
있다. **끄기 자체는 알리고 계정의 연결 상태나 API 응답을 확인하지 않고 먼저 저장한다.**
계정 정보가 잘못되어도 화면의 스위치는 저장된 켜짐 상태를 보여 주므로 끌 수 있다.
예약 목록 조회나 취소 결과를 확인하지 못해도 발송은 꺼진 채로 두고, 이력을 확인하라는
주의를 표시한다. 설정 화면은 채널을 끄면서 함께 취소된·취소하지 못한 건수를 저장 안내
문장에 그대로 보여준다. **템플릿 탭의 가져오기 안내도 같은 결과를 보여준다** —
승인을 잃어 사용할 수 없는 템플릿에 걸려 있던 예약이 있었다면, 몇 개가 취소됐고
몇 개가 취소되지 못했는지를 가져오기 안내 문장에 이어 붙인다. 한쪽 화면은
숫자로 말하고 다른 쪽은 침묵하면, 관리자는 침묵하는 쪽을 "아무 일도 없었다"로
읽는다 — 그래서 두 화면 모두 같은 사실을 같은 방식(숫자, 문장은 서버가 조립)
으로 말한다. 두 화면 모두 취소하지 못한 건이 남았으면 안내를 성공(초록 체크)이 아니라
주의(노랑)로 보여준다 — 초록 체크 아래 "취소하지 못했습니다"가 적혀 있으면 문장을
끝까지 읽지 않은 관리자는 다 끝난 줄 안다.

설정 화면에서 **사용자 ID 나 API 키를 바꿔 저장해도** 두 채널 스위치가 함께 꺼지고
(새 계정에 옛 계정의 확인 상태를 물려주지 않는다), 그때도 같은 자동 취소가 일어난다.
취소 요청은 그 예약을 접수한 **옛 자격증명으로** 먼저 나간 뒤에 새 계정이 저장된다 —
순서가 반대면 옛 계정이 접수한 예약을 새 키로 취소하려 들어 알리고가 거절하고, 그
예약은 GNUCMS 에서 영영 멈출 수 없게 된다. 저장 안내도 끄기 버튼과 같은 문장·같은
색으로 그 숫자를 말한다.

### 수신자가 탈퇴하거나 차단되면

회원이 **탈퇴**하거나 관리자가 회원을 **차단**하면, 그 회원 앞으로 아직 나가지 않은
예약도 함께 취소를 시도한다. 번호를 지우는 것(탈퇴)만으로는 멈추지 않는다 — 예약은
거는 순간 알리고로 넘어가 있고 수신자 행이 번호를 따로 들고 있어서, 아무것도 하지
않으면 탈퇴한 사람의 전화기가 며칠 뒤에 울린다. 차단은 번호를 지우지도 않는다.

**멈출 수 있는 단위는 사람이 아니라 접수 묶음(mid)이다.** 알리고에 "이 묶음의 이
사람만 빼 달라"고 말하는 길은 없다. 그래서 **그 회원 혼자 든 묶음만** 취소하고,
다른 수신자가 함께 든 묶음(500명 묶음 같은)은 그대로 둔다 — 회원 한 사람이 스스로
누르는 탈퇴가 관리자가 걸어 둔 다른 499명의 발송까지 지우는 편이 더 나쁘고, 남은
사람을 다시 접수하는 것은 이 저장소가 스스로 금지한 재발송이다. 멈추지 못한 건은
운영자 로그에 한 줄 남는다. 이미 나간 발송은 취소 대상이 아니고(멈출 것이 없다),
이력에 남은 번호도 지우지 않는다 — 보존은 의도된 설계이고 문제는 보존이 아니라
**새 발송**이다.

취소된 예약은 이력에서 실패가 아니라 **취소**로 센다. 묶음 여럿 가운데 하나만
취소된 작업은 `cancelled`가 되지 않고 `scheduled`로 남는다(나머지는 예정대로 나간다).

### 예약이 결과 조회에 미치는 영향

발송 시각이 아직 오지 않은 예약 건은 §8의 결과 조회 대상에서도, 이력 화면의 "아직
결과를 기다리는 중" 건수에서도 제외된다 — 알리고는 그 시각이 오기 전까지 이 접수
건에 대해 아무것도 모르므로, 미리 물어봐야 조회 예산(화면을 한 번 열 때 5번)만 쓰고
답은 얻지 못한다. 안내와 갱신 버튼이 같은 규칙을 쓰는 것이 중요하다: 세기만 하고
조회하지 않으면 "결과를 기다리는 중 3건"이라 적어 놓고 그 갱신 버튼은 발송 시각이
올 때까지(최대 30일) 알리고를 한 번도 부르지 않는다. 발송 시각이 지나면(=더는 예약이
아니게 되면) 보통 발송과 똑같이 조회 대상이 된다. 7일 뒤 조회를 포기하는 시계(§8)도
접수 요청 시각이 아니라 **발송 시각부터** 잰다 — 접수와 발송 사이에 최대 30일이
벌어질 수 있어서, 접수 시각부터 셌다면 며칠 뒤로 예약한 건이 나가기도 전에
"결과를 알 수 없음"이 될 수 있기 때문이다.

## 8. 결과 갱신은 방문 기반이다 — CLI는 선택 사항이다

알리고는 **결과를 알려 주는 웹훅이 없다.** 발송 직후에는 접수만 확인될 뿐, 실제
전달 성공·실패는 알리고에 따로 물어봐야 안다. `docs/extensions.md`가 정한 대로
GNUCMS의 어떤 기능도 주기적 실행에 호스팅 cron을 요구하지 않으므로, 결과 조회도
**관리자가 운영 → 알림톡·문자 발송 → 이력 화면을 열 때마다** 조금씩 갱신된다. 한
번 열 때 알리고에 묻는 횟수는 **최대 5번**이다 — 알림톡 결과 대기열과 대체문자
결과 대기열이 이 예산을 나눠 쓰므로, 두 대기열을 합쳐 5번을 넘지 않는다. 그래서:

- **접속이 없으면 결과 갱신도 늦어질 수 있다.** 이력 화면은 "아직 결과를 기다리는
  중인 발송이 N건 있습니다. 접속이 없으면 갱신이 늦어질 수 있습니다"를 보여주며
  그 자리에 수동 **갱신** 버튼을 둔다. 이 사실을 숨기지 않는다.
- 발송한 지 오래됐는데도(7일) 결과가 안 잡히는 건은 더 조회하지 않고
  `message_recipients.status`를 `unknown`으로 바꿔 "결과를 알 수 없음"으로
  표시한다. 무한히 다시 묻지 않는다.
- 조회 자체가 실패하면(계정 미설정, 키 취소, 접속 불가) 목록은 저장된 값 그대로
  보여주되 **그 사유를 화면 위에 적는다.** 실패를 조용히 삼키면 결과가 이유 없이
  "결과를 알 수 없음"으로 바뀌는 것만 보여 관리자가 손쓸 수 없다.

cron을 쓸 수 있는 호스팅이라면 `bin/messages.php`로 같은 갱신을 더 자주 돌릴 수
있다. **이 CLI가 없어도 기능은 그대로 동작한다** — 있으면 결과가 조금 더 빨리
반영될 뿐이다. cron 등록은 완전히 선택이며 GNUCMS의 어떤 기능도 이 CLI가 실행되고
있다고 가정하지 않는다.

```
php bin/messages.php refresh                       config/config.php 를 읽어 최대 20건 갱신
php bin/messages.php refresh 50                     최대 50건 갱신 (두 대기열 합계)
php bin/messages.php refresh 50 /경로/config.php     다른 설정 파일을 쓴다
```

성공하면 갱신한 건수를 출력하고 종료 코드 0을 낸다. 여러 번 돌리거나 겹쳐 돌려도
안전하다 — 이미 결과가 잡힌 건은 다시 조회하지 않고, 관리자 화면 방문과 같은 조회
대기열을 공유한다.

## 9. 회원 휴대폰번호

회원에게 알림톡·문자를 보내려면 `users.phone`에 번호가 있어야 한다. 번호는 세 자리에서
들어온다.

- **가입 화면**: 설정 → 회원·글쓰기의 **가입 시 휴대폰번호**가 `받지 않음`(기본) ·
  `선택 입력` · `필수 입력` 중 하나를 정한다. 기본이 `받지 않음`인 것은 이 기능을 들이면서
  기존 사이트의 가입 흐름을 바꾸지 않기 위해서다.
- **회원정보 수정**: 가입 수집 설정과 무관하게 주문·알림용 휴대폰번호를 입력할 수 있다.
  `필수 입력`이고 저장된 번호가 있으면 비울 수 없다. 닉네임과 별도로 주문자명을 저장하며
  최초 주문에서 입력한 이름·휴대폰은 주문 접수가 성공했을 때 미등록 회원정보에 저장한다.
- **관리자 회원 수정**: `signup_phone` 정책과 **무관하게** 언제나 번호 칸을 낸다. 그 정책은
  "가입 화면이 무엇을 묻는가"이지 "이 사이트가 번호를 다루는가"가 아니다.

번호는 저장할 때 `GnuCms\Aligo\PhoneNumber::normalize()`를 거쳐 숫자만 남는다. 본인확인은
하지 않고 형식만 본다. 회원 관리 목록에서는 번호로 검색할 수 있고 목록에는 가운데를 가려
보여준다. 탈퇴하면 번호도 함께 지우고, 그 회원 앞으로 걸려 있던 예약 발송도 함께
멈춘다(§7) — 탈퇴는 이 시스템이 개인정보를 놓아주겠다고
약속하는 자리인데 가장 연락하기 쉬운 값만 남겨 둘 수는 없기 때문이다.

발송 탭의 회원 고르기는 정상 상태(`active`)인 회원만 찾으며, 번호가 없는 회원은 목록에
**번호 없음**으로 나온다. 번호를 직접 입력하거나 붙여넣는 길은 그대로 열려 있다.

## 10. 코어 알림과 공통 발송 설정

코어 알림은 `GnuCms\Notify\Notifier`를 통해 발송한다. 관리자는 **설정 → 알림·발송**
(`/admin/settings/messaging`)에서 이메일·알림톡·문자의 사용 여부를 한 번 설정한다.
각 알림은 메일·문자 선택과 공통 설정이 모두 허용해야 보낸다. 문자는 공통 네 가지 발송 방식에 따라 처리한다.
설정 → 알림별 발송 규칙(`/admin/settings/notifications`)에서는 메일·문자 체크박스와 문구·알림톡 템플릿 연결을 관리한다.
선택을 저장하기 전에는 현재 공통 설정을 따르는 동작을 유지하고, 과거 개별 알림톡·문자 ON/OFF는 사용하지 않는다.
목록은 회원가입·인증, 비밀번호, 댓글·답글, 주문 접수·결제·준비·배송·취소·환불, 상품문의 답변 순이다.
전체 이벤트와 변수는 `Notify\Events`를 기준으로 하며 최신 화면 규칙은 [sms-admin.md](sms-admin.md)를 따른다.

### 기본 문구와 간단한 템플릿 연결

- 문자에는 알림별 기본 문구가 있어 별도 저장 없이 쓸 수 있다. 빈 문구를 저장하면 기본 문구를 사용한다.
  수정할 때는 기존 변수·인코딩·길이 검증을 적용하고, 기본 이메일 문구와 회원 이메일 수신거부를 유지한다.
- 알림톡에는 현재 발신프로필의 사용 가능한 승인 템플릿을 연결한다. 같은 이름의 변수는 자동으로 연결하고 고객명·회원명은 이름,
  회사명·서비스명은 사이트명으로 연결한다. 기존 사용자 지정 연결은 유지하고, 알 수 없는 변수만 수동으로 고른다.
- 문구 편집·변수 연결·발송 시점과 예시 미리보기는 접힌 상세 항목에 둔다. 오류가 있는 항목은 펼쳐 보여 준다.
  선택과 문구·템플릿 저장은 알림별로 처리하며, 그 저장으로 공통 채널 설정은 바뀌지 않는다.
- 인증 등 이메일 전용 이벤트에는 전화 채널을 적용하지 않는다. 알림함을 지원하는 이벤트는 항상 기록한다.
  문자·알림톡은 번호가 있는 수신자에게만 보내며 이메일 수신거부 정책은 [notification-channel-policy.md](notification-channel-policy.md)를 따른다.

### 승인·템플릿 유효성 확인

알림톡은 읽을 때마다 현재 발신프로필 템플릿의 존재·승인·중단 상태와 변수 연결을 다시 확인한다. 미연결이거나 유효하지 않으면
알림톡을 보내지 않고, 알림별 문자를 선택하고 공통 설정이 허용하면 문자로 보낸다. 이런 경우에도 이메일·문자 문구는 저장할 수 있다.
사용할 수 없는 템플릿 참조는 명시적인 지우기 체크로 제거하며, 그 사이 다시 유효해진 연결은 지우지 않는다.
공통 채널이 꺼져도 저장한 문구·템플릿은 유지한다.

### 보내는 차례와 실패

알림함 → 메일 → 알림톡 순서로 시도한다. 알림톡이 꺼져 있거나 사용할 수 없거나 접수에
실패하면, 문자가 켜져 있을 때 문자 채널을 시도한다. 알림톡이 접수된 뒤 배달에 실패하면
알리고의 문자 대체발송을 사용한다. 대체문자는 알림 설정의 문자 본문으로 나간다. 메일은
앞선 발송의 시간 예산을 다 쓴 경우에도 항상 시도한다.

**건너뛰기와 실패는 다르다.**

- **건너뛰기** — 켜 둔 채널이 지금 이 수신자에게 전할 수단이 없거나(번호 없는 회원의
  알림톡·문자, 회원이 아닌 수신자의 알림함) 보낼 내용이 갖춰지지 않았다(못 쓰게 된 알림톡 템플릿). 실패가 아니므로 **나머지 채널은 그대로 나간다** —
  번호가 없다는 이유로 메일까지 막히면 안 된다.
- **실패** — 보낼 수 있다고 해 놓고 발송이 터졌다. **그 채널만** 실패한 것이고 나머지는
  계속 간다(비밀번호 재설정은 문자가 죽어도 메일로 가야 한다). 실패는 터진 그 자리에서
  바로 운영자 로그에 남는다 — 모아 두었다가 끝나고 적으면 뒤 채널이 프로세스째 죽었을 때
  그 기록도 함께 사라진다. **알리고가 받지 않은 발송도 실패다**: 발송 엔진은 알리고가
  거절하거나 응답이 없어도 작업 행을 남기고 정상적으로 돌아오는데(관리자 일괄 발송에서는
  그것이 맞다 — 일부만 실패한 작업도 이력에 남아야 한다), 알림 쪽은 그 작업의 접수 결과를
  다시 읽어 한 건도 접수되지 않았으면 실패로 다룬다. 이것이 없으면 `message_jobs` 에
  `실패`가 적히는 그 요청에서 화면은 「보냈습니다」를 그린다.
- **시간 초과** — 앞선 채널이 이 요청의 발송 시간(6초)을 다 썼으면 남은 전화 채널은
  **이번에 시작하지 않는다**. 메일과 알림함은 계속 시도한다. 운영자 로그에는 포기한
  채널을 남긴다.
- **한 채널이라도 실제로 나갔으면 오류가 아니다.** 시도한 채널이 있는데 한 곳도 성공하지
  못했을 때만 오류를 올린다 — 아무 데도 안 갔는데 화면이 "보냈습니다"라고 말하면 안 되기
  때문이다. 켜 둔 채널이 전부 건너뛰기였던 경우는 오류가 아니라 로그 한 줄이다(번호 없는
  회원 하나 때문에 가입 자체가 실패하면 안 되지만, "켜 두었는데 아무 데도 나가지 않는다"는
  사실은 운영자가 알아야 한다). 공통 메일 설정이 켜져 있으면 코어 알림에 메일 채널이 포함된다.

**재시도는 하지 않는다.** 실패한 채널을 다시 부르지 않고, 화면도 "잠시 후 다시 시도해
주세요"라고 말하지 않는다. 문자·알림톡은 상대 서버가 메시지를 받아들인 **뒤에도** 응답을
못 받은 채 끊길 수 있고, 그때 한 번 더 보내면 진짜 전화기로 두 통이 간다. 그래서 전부
실패했을 때 사람이 보는 문장은 "다시 보내면 같은 알림이 두 번 갈 수 있으니 관리자에게 알려
주세요"다 — 다시 보낼지는 사람이 정한다.

**로그에는 진짜 이유를, 화면에는 일반적인 문장을.** 알리고 응답이나 DB 오류를 화면에 그대로
실어 보내지 않는다. 로그 한 줄에는 예외 클래스·문구와 거절 사유만 적고, **수신자(번호·주소)도
변수값(링크·토큰)도 적지 않는다** — 비밀번호 재설정 링크가 로그에 남으면 그 로그를 읽는
사람이 계정을 가져갈 수 있다. 사유 안에 `key`·`secret`·`password`·`token`·`auth` 같은 조각이
이름에 들어간 칸이 있으면 그 값은 `***`로 가리고(이름은 적는다 — 어느 칸이 거절했는지는
알아야 한다), 나머지 값도 200자에서 자른다.

### 링크를 보낼 수 없으면 가입을 받지 않는다

인증 링크가 갓 가입할 사람에게 닿을 수 없으면 **회원 행을 만들기 전에** 가입을 거절한다
("지금은 회원가입을 받을 수 없습니다…"). 받아 버리면 회원 행은 만들어졌는데 인증 링크는
아무 데도 가지 않고, 인증 전에는 로그인이 막히므로 그 사람은 자기 계정 밖에 갇힌 채
"메일함을 확인하세요" 화면만 보게 된다. 문구만 바꿔서는 그 자리를 벗어날 수 없으므로 문
앞에서 돌려보낸다 — 남는 찌꺼기도 없고, 관리자가 채널을 다시 켜면 그대로 가입할 수 있다.
첫 사람(사이트 소유자)은 인증 없이 만들어지므로 이 검사를 받지 않는다.

**"채널이 켜져 있는가"로는 모자란다.** 알림함 하나만 켜 두면 켜져 있기는 한데 `email_verify`는
알림함이 받지 않으므로 인증 링크는 영영 아무 데도 가지 않는다. 그래서 묻는 것은 "켜져
있는가"가 아니라 "**이런 모양의 사람**에게 닿는가"다.

가입 뒤 화면(`/register`)과 비밀번호 재설정 요청 화면(`/forgot-password`)은 그 주소에 계정이
있든 없든 **똑같은 응답 본문**을 낸다(**응답 시간까지 같지는 않다** — 바로 아래 참고).
두 화면이 말하는 것은 "당신에게 보냈다"가 아니라 "이 설정으로
누구에게든 보낼 수 있다"뿐이다 — 앞의 것을 말하는 순간 그 화면은 가입 여부를 묻는 도구가
된다. 그래서 답은 수신자를 찾지 않고 **모양**으로만 정해진다. 그 대가로 남는 빈틈은 하나다:
문자만 켜 둔 사이트에서 번호가 없는 회원은 재설정 링크를 못 받는데 화면은 보낼 수 있다고
말한다. 그 사실은 운영자 로그에 남는다.

**같은 것은 본문이고, 시계는 아니다.** 실제 발송은 계정이 있는 주소에서만 일어나므로,
전화 채널을 켜 두면 그 주소 쪽 응답이 알리고 왕복만큼 눈에 띄게 느리다(재 보니 0.0002초
대 0.3초였고, 실제 왕복이 1~2초면 차이도 그만큼 벌어진다). 이 차이는 이 분기가 만든 것이
아니다 — 갈라진 적 없는 판에서도 메일은 계정이 있을 때만 나갔다. 발송이 방문 요청 안에서
일어나고 큐도 cron 도 없는 이 구조에서 시간까지 맞추려면 없는 주소에도 인위적 지연을
넣어야 하는데, 그 지연은 그 자체로 새로운 부하 창구가 된다. 그래서 시간을 맞추는 대신
**수확 속도를 묶는다**: 바로 아래의 한도(주소마다 10분 3회, 한 회선마다 10분 5회)가
조회 **전에** 세므로, 한 회선에서 10분에 다섯 주소밖에 시험할 수 없다.

휴대폰번호가 없는 회원은 알림톡·문자를 건너뛰고 메일을 받는다. 비밀번호 재설정 메일도
항상 시도하므로 전화 채널만 켜져 계정을 되찾지 못하는 설정은 생기지 않는다.

**재설정 요청에는 횟수 제한이 있다.** `/forgot-password` 는 로그인 없이 누구나 누를 수 있는데,
`password_reset` 을 문자·알림톡으로 켜 두면 누를 때마다 남의 전화기가 울리고 잔여 건수가
줄어든다. 그래서 **주소마다 10분에 3회, 한 회선(IP)마다 10분에 5회**까지만 받는다. 주소 쪽
한도는 IP 를 가리지 않는다 — IP 만 바꿔 가며 같은 번호로 계속 보내는 것이 막으려는 일이기
때문이다. 세는 자리는 주소를 찾아보기 **전**이라, 가입된 주소든 아니든 똑같이 세고 똑같이
잠긴다: 잠겼다는 사실이 계정의 존재를 말하지 않는다. 다만 **이메일 형태가 아닌 값은 세지
않는다** — 그런 값은 어떤 회원과도 맞지 않아 한 통도 나가지 않는데, 값마다 잠금 표에 영구
행이 하나씩 생긴다(로그인 쪽이 같은 이유로 같은 조건을 쓴다).

### 알림도 발송 이력에 남는다

알림톡·문자로 나간 알림은 관리자 발송 화면과 **같은 문**(`Dispatch::send()`)을 지난다.
그래서 **알림 한 통마다 `message_jobs` 행 하나**가 생긴다(한 알림에 알림톡과 문자를 함께
켜 두었으면 채널마다 하나씩이다). 일부러 그렇게 두었다 — 진짜로 돈이 드는 발송이고
운영자가 이력에서 봐야 하는 건이다. 알림용으로 더 가벼운 두 번째 발송
경로를 만들지 않는다(그 경로는 채널 허용 스위치·길이 분류·중복 제거·결과 조회를 저마다 다시
틀리게 구현할 자리가 된다). 메일과 알림함은 이 표를 쓰지 않는다.

**비밀이 담긴 값은 수신자 본문에 남지 않는다.** 비밀번호 재설정·이메일 인증·소셜 이메일
확인 링크에는 그 링크를 가진 사람이 계정을 가져갈 수 있는 토큰이 들어 있다. 코어는 그 토큰을
되돌릴 수 있는 형태로 저장하지 않으므로(§11), 이력의 수신자별 본문에도 남기지 않는다 —
실제로 나가는 문자·알림톡에는 링크가 그대로 들어가고, `message_recipients.body` 에만 그 값이
`***` 로 적힌다(「홍길동님 *** 에서 재설정하세요」). 작업 본문(치환 전 원문)은 그대로이므로
무슨 문구가 나갔는지는 이력에서 그대로 읽을 수 있고, 잃는 것은 그 한 사람에게 나간 링크
원문뿐이다.

어느 알림이 그 작업을 만들었는지는 `message_jobs.event_key`에 남는다. **비어 있으면 관리자가
손으로 보낸 것**이다. 이력 목록에는 **알림** 열로 보이고, 목록 위 드롭다운으로 전체 · 관리자
수동 발송 · 알림별로 거를 수 있다.

### 새 댓글 알림은 양이 는다

`comment_new`는 받을 사람이 둘일 수 있다 — 글쓴이("내 글에 댓글")와, 답글이면 부모 댓글
작성자("내 댓글에 답글"). 둘이 같은 사람이면 한 번만 보내고, 댓글을 쓴 본인에게는 보내지
않는다. 사람마다 따로 보내므로 한 사람에게 실패해도 다른 사람은 받고, **사람마다, 그리고
켜 둔 전화 채널마다** `message_jobs` 행이 하나씩 생긴다 — 받을 사람이 둘인 댓글에 알림톡과
문자를 모두 켜 두었으면 댓글 한 건이 **네 행**이 된다. 댓글이 활발한 사이트에서 이 알림의
문자·알림톡을 켜면 이력이 그 작업으로 가득 차고 발송 비용도 그만큼 든다 — 켜기 전에 감당할
수 있는 양인지 확인한다.

받는 사람이 정상 상태(`active`) 회원이 아니면 건너뛴다. 알림 발송이 실패해도 댓글 등록은
막지 않는다 — 댓글은 이미 저장된 뒤에 알림을 보내므로, 여기서 오류를 내면 사람은 같은 댓글을
한 번 더 쓴다.

**댓글을 쓴 사람이 그 발송을 기다린다.** 이 알림은 댓글 등록 요청 안에서 그 자리에 나간다.
호스팅 cron 을 요구하지 않는 구조라(확장 문서 참고) 뒤로 미룰 곳이 없기 때문이다 — 큐에
넣어 두면 그것을 꺼낼 사람이 없다. 그래서 상한을 둔다: **한 요청에서 알림 발송에 쓰는 시간이
6초를 넘으면 그 요청의 남은 채널·남은 수신자는 보내지 않고** 운영자 로그에 무엇을 포기했는지
남긴다. 알리고가 정상일 때는 걸리지 않는 값이고(왕복은 보통 1초 아래다), 걸린다는 것은 이미
무언가 느리다는 뜻이다. 대가는 분명하다 — 알리고가 흔들리는 동안 **일부 알림은 아예 나가지
않는다**(다시 보내지도 않는다). 그 대신 댓글 한 건이 40초짜리 화면이 되지는 않는다.

### 이 목록은 확장이 늘릴 수 없다

알림 일곱 개는 코어가 고정한 목록(`Notify\Events::ALL`)이고, 확장이 알림을 더하거나 이 설정을
바꾸는 API는 없다. 확장이 메시지를 보내려면 §6의 `$app->aligo()->send()`를 쓴다 — 그 발송은
`event_key`를 싣지 않는 한 이력에서 관리자 수동 발송과 같은 갈래로 보인다.

## 회사 정보와 문의처 변수

### 카카오 알림톡 전용 발신 정보

설정 → 문자·알림톡(`/admin/aligo#alimtalk-info`) 상단의 **알림톡 발신 정보**에서 서비스명·홈페이지 주소·문의처를 따로 입력하고 저장한다. 각각 템플릿의 `#{사이트명}`·`#{사이트주소}`·`#{문의처}`에 들어간다. 서비스명은 100자, 주소는 1,000자, 문의처는 500자 이내로 입력하며 주소는 HTTP 또는 HTTPS 전체 주소를 사용한다. 모두 선택 입력이고 빈 값으로 저장하면 해당 항목을 사이트 기본 정보로 되돌린다.

알리고 계정 설정과 별도 POST(`/admin/aligo/info`)로 저장하며 API 키·채널 스위치·예약을 변경하지 않는다. 기존 `site_settings`의 `alimtalk.info.name`, `alimtalk.info.url`, `alimtalk.info.contact`만 저장하므로 DB 구조를 변경하지 않는다. 관리자 권한과 CSRF 검증을 거쳐 저장하고 입력 오류 시 입력값을 유지한다.

자동 알림톡은 발송 시점에 전용 정보를 읽는다. 관리자 직접 알림톡 발송에서도 같은 정보를 사용하며 해당 세 변수는 읽기 전용으로 보여 준다. 일반 문자와 이메일에는 기존 사이트 정보를 사용하고, 알림톡 API에서 요청한 대체문자에는 해당 알림톡에 적용한 정보를 사용한다. 이미 알리고에 접수한 예약 메시지는 접수 당시의 정보로 발송된다.

### 사이트 기본 정보

템플릿의 서비스명은 `#{사이트명}`, 홈페이지 주소는 `#{사이트주소}`로 작성한다. 자동 발송 시 각각 사이트 설정의 `site_name`과 설치 환경의 `app.url`로 치환한다. 이벤트별 상세 확인 주소는 기존 `#{링크}`를 사용하며 회원·주문별 실제 링크로 치환한다. 템플릿 본문에 GNUCMS나 특정 도메인을 고정하지 않는다. 관리자 직접 발송에도 사이트명·사이트주소의 기본값을 자동으로 채운다.

설정 → 기본·홈(`/admin/settings#company`)의 회사 정보에서 회사명, 회사 전화, 회사 이메일을 저장한다. 전화로 보낼 수 있는 코어 알림에는 `#{문의처}` 변수를 제공한다. 알림톡 템플릿의 `문의처`를 같은 이름의 코어 변수에 연결하면 발송 시점에 회사 전화와 이메일을 `전화 / 이메일` 형태로 넣는다. 둘 다 없으면 `app.url`의 사이트 주소를 쓴다. 직접 발송의 문의처도 기본값을 채운다. 기존 site_settings를 사용하며 회사 정보 저장만으로 메시지를 발송하거나 채널을 켜지는 않는다.

## 11. 보안

- API 키는 화면·로그·예외 메시지 어디에도 원문으로 실리지 않는다. 알리고 응답
  원문도 그대로 노출하지 않고, 사유만 정리해서 보여준다.
- 이력 **목록**은 작업 단위라 수신번호 자체가 나오지 않는다. 번호는 작업 **상세**에서
  수신자별로 전체가 그대로 보인다.
- 알림톡·문자 화면은 전역 관리자만 열 수 있다.
- 비밀번호 재설정·이메일 인증 토큰은 `user_tokens` 에 sha256 으로만 남는다. 그 링크가
  문자·알림톡으로 나가더라도 발송 이력의 수신자 본문에는 값이 `***` 로 적혀, 백업에
  살아 있는 토큰이 평문으로 따라다니지 않는다(§10 "알림도 발송 이력에 남는다").


## 알리고 반환 비용

알림톡 발송 API의 `info.unit`·`info.total`을 발송 접수 시점에 `message_jobs.provider_costs`에 묶음별 발송 ID, 성공·실패 접수 건수, 기록 시각과 함께 저장한다. 숫자는 최대 소수 여섯 자리 십진 문자열로 보관하고 합산은 정수로 한다. 발송 이력 목록의 발송 정보와 상세 화면은 반환 금액이 있을 때만 비용을 포인트 단위로 표시한다. 묶음 일부만 금액을 반환하면 그 합계에 일부 응답임을 표시한다.

문자 API는 현재 금액을 반환하지 않는다. 단가 설정·예상 금액·단가 미설정 안내는 만들지 않는다. 금액이 없거나 기존 이력인 경우 항목을 표시하지 않으며 0원으로 간주하지 않는다. 결과 조회 API에는 비용이 없어 과거 기록을 역산·보충하지 않는다. 반환 비용은 접수 당시 API 값이며, 실패 환불·예약 취소·대체문자의 최종 비용으로 재계산하지 않는다. 이후 정산은 별도의 실제 정산 자료와 대사해야 한다.

근거: https://smartsms.aligo.in/alimapi.html (`info` 전송 응답), https://smartsms.aligo.in/admin/api/spec.html (문자 응답).


## SMS 비용을 줄이는 기본 문구

가입·댓글·상품문의·주문 상태 기본 문구는 핵심 상태 위주로 간결하게 표시한다. 주문 문자에는 주문번호·상태·짧은 조회 주소를 넣고 이름·금액·운송장·환불 상세는 주문 화면과 메일에서 확인한다. 회원 복구 알림은 일회용 인증 링크와 유효시간을 유지한다.

SMS와 알림톡 대체문자의 링크는 같은 사이트의 `/s/orders`(본인 주문 목록), `/s/notice`(본인 알림함), `/s/password`(비밀번호 찾기)를 사용한다. 고정 목적지로만 이동하고, 기존 로그인·주문 소유권 확인을 그대로 따른다. 주문 문자는 특정 주문번호를 본문에 표시하고 조회 링크는 주문 목록으로 연결한다. 외부 단축 URL 서비스와 공개 임의 URL 등록은 사용하지 않는다. 메일·승인된 알림톡 링크와 본문은 유지한다.

예전 기본 문구와 정확히 같은 저장값만 배포 시 새 기본 문구로 변경하고 사용자 편집 문구는 보존한다. 치환된 실제 본문의 EUC-KR 90바이트 이하면 SMS, 초과하면 LMS로 처리하는 기존 분류를 유지한다. 긴 사이트명·편집 문구·인증 링크를 억지로 자르거나 여러 SMS로 나누어 보내지 않는다.

문자용 주소는 목적지를 명확하게 드러내는 `/s/orders`, `/s/notice`, `/s/password`를 생성한다. 이미 발송한 문자의 `/s/o`, `/s/n`, `/s/p`도 동일한 화면으로 계속 연결한다. 기본 비밀번호 변경 문구는 긴 경로에서도 SMS 범위에 맞도록 간결하게 유지한다.

알림함 문자 주소는 `/s/notice`로 생성하며, 이전 `/s/notifications`도 호환 경로로 계속 연결한다.
