# 작은 쇼핑몰 운영 안내

한 사람이 상품·재고·배송·반품·정산을 관리하는 회원 전용 쇼핑몰이다. 상품 조회와 장바구니는 로그인 없이 사용할 수 있고, 주문·배송지·신청 내역은 해당 회원과 전역 관리자에게만 공개한다.

## 패키지와 결제 방식

| 패키지 | 역할 | 실행 주소 |
| --- | --- | --- |
| `modules/shop` | 상품, 주문, 배송, 반품·교환·환불, 재고, 정산 | `/modules/shop/admin` |
| `plugins/payment-inicis` | KG이니시스 카드결제 | `/plugins/payment-inicis/settings` |
| `plugins/payment-kcp` | NHN KCP 카드결제 | `/plugins/payment-kcp/settings` |
| `plugins/payment-kspay` | KSPay / KSNET 카드결제 | `/plugins/payment-kspay/settings` |

**세 플러그인의 연동 방식은 PortOne V2다.** PortOne 계정, 결제사별 채널, V2 API Secret, 웹훅 서명 시크릿이 필요하다. 결제사 가맹점 계약 및 채널 개통은 실제 운영자가 진행한다. PG 직접 연동용 SignKey·인증서·API Key를 GNUCMS 설정에 넣지 않는다. 해당 값은 PortOne의 PG 채널 설정에서 관리한다.

세 플러그인은 각각 활성화·설치·환경 설정을 관리하며, 공통 PHP 결제 계약을 구현한다. 쇼핑몰은 원하는 결제 플러그인만 켜서 사용할 수 있다. 이니시스가 중복 표기된 요청은 같은 결제사로 처리했다.

지원 결제 범위는 **KRW 일반 과세 상품의 카드결제, 전체·부분 취소**다. PC·모바일 결제창은 PortOne 브라우저 SDK를 사용한다. 카드번호를 GNUCMS가 입력받거나 저장하지 않는다. 가상계좌, 계좌이체, 휴대폰, 빌링, 에스크로, 면세·복합과세, 쿠폰·적립금, 차액 결제는 현재 범위에 포함하지 않는다. 교환은 동일 상품의 동일 가격 옵션으로 처리하고, 가격 차이가 있는 상품은 반품 후 새 주문으로 처리한다.

## 설치와 판매 시작

1. 관리자 → 플러그인에서 사용할 결제 플러그인을 활성화한다.
2. 결제 플러그인 설정에서 **데이터 설치**를 실행한다. GET 조회만으로 테이블을 설치하지 않는다.
3. 테스트 환경에 PortOne 상점 ID, 해당 PG의 테스트 채널 키, V2 API Secret, 웹훅 서명 시크릿을 저장한다. API 실행을 허용한다.
4. 관리자 → 모듈에서 작은 쇼핑몰을 활성화하고 **쇼핑몰 데이터 설치**를 실행한다.
5. 상점 설정에서 상호·대표자·사업장·연락처·반품 주소와 실제 운영에 맞는 배송·반품·개인정보 처리 정책을 입력한다. 개인정보 보관기간 및 결제·택배 위탁 정보도 운영 정책에 명시한다.
6. `config/config.php`의 `app.url`을 외부에서 접근 가능한 HTTPS 사이트 주소로 설정한다. 하위 경로 설치는 `https://example.com/cms`처럼 경로까지 포함한다.
7. 상품을 등록하고 관리자로 테스트 주문, PC·모바일 결제, 웹훅, 부분·전체 취소를 검증한다. 테스트 상점에서는 관리자만 주문·결제할 수 있다.
8. 운영 채널을 별도로 저장하고 API 실행을 허용한 뒤 상점의 결제 환경을 운영으로 바꾼다. 주문 접수를 연다.
9. CMS 사이트 메뉴에 `/modules/shop/catalog`를 추가해 상점으로 연결한다.

운영 서버에서 Composer·npm 설치나 빌드를 하지 않는다. PHP 코드와 정적 템플릿은 배포본에 포함하고, 결제창에서만 공식 CDN의 브라우저 SDK를 읽는다. 주문·정산 화면의 PHP·CSS에는 새 패키지 의존성이 없다. 이미지와 런타임 잠금은 `storage/` 또는 기존 업로드 설정 경로에 저장한다.

## 상품과 옵션

- 상품별 옵션 종류는 최대 두 개다. 예: 색상과 사이즈.
- 종류별 값은 쉼표로 구분한다. 각 종류는 20개 값까지, 전체 조합은 100개까지다. 옵션을 사용하지 않으면 이름과 값을 비운다.
- 각 조합에 가격과 판매 가능 재고를 설정한다. 새 조합의 초기 가격·재고와 기존 조합의 수정 입력을 구분한다.
- 상품명·설명은 텍스트로 저장하고 출력 시 이스케이프한다. 상품 대표 이미지는 JPG·PNG·WebP, 5MB 이하, 가로·세로 8,000px 이하를 지원한다.
- 삭제 대신 공개/비공개와 옵션 사용 상태로 관리한다. 과거 주문은 주문 당시 상품명·옵션·단가·배송비를 보존한다.
- 장바구니는 최대 20개 옵션, 옵션별 99개다. 모든 금액은 정수 원으로 계산한다.

## 주문과 재고

```text
결제 대기 → 결제 완료 → 상품 준비 → 배송 중 → 배송 완료
    └ 주문 취소             └ 배송 전 전액 환불
                                      배송 후 → 반품·교환 신청
```

주문 생성 시 가격과 배송비를 서버에서 다시 계산한다. 사용자가 확인한 금액과 다르면 주문을 거절하고 다시 확인하도록 안내한다. 정책 동의 시각과 당시 정책을 주문에 보존하며, 배송지는 암호화한다.

재고는 주문 생성 시 확보한다. 옵션의 판 번호와 재고를 조건부 SQL로 함께 검사하므로 마지막 한 개에 동시 주문이 들어와도 한 주문만 확보한다. 장바구니에 담은 시점에는 확보하지 않는다. 대기 주문은 회원당 다섯 개까지다.

결제 기한은 30분이다. 새 주문 생성 시와 관리자의 미결제 정리 작업에서 만료 주문을 정리한다. 방문과 관계없이 정리하려면 다음 CLI를 스케줄러에서 실행한다. 한 번에 최대 100건을 처리한다.

```sh
php modules/shop/bin/maintenance.php expire
```

취소·만료된 주문에서 늦게 승인이 도착하면 출고하지 않고 같은 요청 키로 전액 취소한다. 취소 결과가 불명확하면 재고를 다시 확보하지 않고 확인 필요 상태로 보존한다. 자동 재취소는 최초 요청 후 2시간 이내로 제한한다.

재고 화면은 판매 가능 수량, 주문 확보 수량, 출고 전 보유 합계를 보여준다. 최근 100건의 초기 입고·수정·주문·취소·반품·교환 변동을 함께 확인할 수 있다. 재고 수정 도중 새 주문이 발생하면 오래된 화면의 수량 덮어쓰기를 거절한다.

## 결제 검증과 웹훅

결제창을 열기 전에 서버에서 결제 ID·금액·통화를 사전 등록한다. 결제창의 성공 응답만으로 결제 완료 처리하지 않는다. 서버 조회에서 다음을 확인한다.

- 주문번호, 상점 ID, 채널 키, 결제사, 테스트/운영 채널 유형
- 통화, 총 금액, 면세액 0, 카드결제 수단
- 거래 ID와 확정 취소 내역·누적 환불 금액의 일치

웹훅 URL은 주문에 사용한 설정 판을 포함하여 결제창에 전달한다.

```text
https://example.com/modules/shop/webhook?provider=inicis&revision=<주문 설정 판>
```

웹훅은 원문 HMAC 서명, 메시지 ID, 시각을 검사한다. 허용 시각 차이는 5분이며 서버 시계를 동기화해야 한다. JSON 요청은 64KB로 제한한다. 콜백의 금액·상태를 신뢰하지 않고 다시 서버 조회한다. 주문 잠금과 원장 고유 키로 재전송·동시 콜백을 중복 반영하지 않는다. 시크릿과 결제사 원문 응답은 로그·템플릿·원장에 저장하지 않는다.

API 대상은 고정 HTTPS 호스트이며 TLS 인증서를 검증하고 HTTP 리다이렉트를 따르지 않는다. 각 요청의 응답 대기는 60초다. API 실행 허용을 해제하면 신규 결제와 조회·환불을 정지한다. 플러그인 사용 중지와 기존 주문 환불 완료 여부를 함께 확인한다.

브라우저 복귀가 중단되거나 웹훅을 놓치면 주문의 **결제·환불 상태 조회**를 사용한다. 정기적으로 미확정 주문을 조회하려면 다음 명령을 사용한다. 최근 7일간 결제창을 연 대기·취소 주문, 확인 필요 주문, 보류 환불을 오래 조회하지 않은 순서대로 처리한다.

```sh
php modules/shop/bin/maintenance.php reconcile --limit=20
php modules/shop/bin/maintenance.php sync --order=<주문번호>
```

별도 설정 파일은 `--config=/절대경로/config.php`로 지정한다. 명령은 쇼핑몰 활성 상태와 API 실행 허용을 존중한다. 스케줄러에 5~10분 간격으로 등록할 수 있으며, CLI 오류는 주문·연결 정보를 노출하지 않는다.

## 취소·반품·환불

배송 전에는 고객이 취소 신청을 하거나 운영자가 전액 취소할 수 있다. 열린 취소 신청이나 미확정 환불이 있으면 출고를 막는다.

상품 준비·출고와 교환품 발송 직전에 결제사 상태를 다시 조회한다. 외부 취소나 진행 중 취소가 확인되면 출고하지 않고 결제 대조를 요구한다.

반품은 다음 순서로 처리한다.

1. 고객 또는 운영자가 주문 상품과 수량, 사유를 지정해 접수한다.
2. 운영자가 승인하거나 사유와 함께 거절한다. 거절하면 다시 신청할 수 있다.
3. 회수·검수 완료를 기록하고 재판매 가능 여부를 선택한다.
4. 반품 상품 금액을 확인하고 최초 배송비 환불 여부, 정책에 따라 고객과 확인한 반품 비용 공제액을 지정한다.
5. 환불을 요청한다. 서버 조회로 취소가 확정된 뒤에만 반품 완료 수량과 재판매 가능한 재고를 반영한다.

환불 금액은 `주문 당시 단가 × 반품 수량 + 선택한 최초 배송비 − 반품 비용`이다. 최초 배송비는 한 번만 환불할 수 있다. 누적 환불이 결제 금액을 초과하거나 이미 처리·신청한 수량을 다시 신청하는 것을 거절한다. 반품 비용이 상품 환불액 이상인 0원 환불은 지원하지 않는다.

환불 요청은 외부 호출 전에 DB에 저장한다. 결제 취소 API에 고유한 멱등 키와 취소 전 잔액을 함께 보내고, 동일 요청의 금액·사유·키를 유지한다. 한 주문에서 불명확한 환불이 있으면 새 환불을 만들 수 없다.

- 응답 유실: 먼저 상태 조회한다. 결제사에서 취소가 성공했으면 이 조회만으로 기존 환불을 완료한다.
- 2시간 이내: 기존 환불의 재확인·재요청 버튼을 사용한다.
- 2시간 초과: 자동 재전송하지 않는다. 결제사 관리자에서 성공 여부를 직접 확인한다.
- 결제사에서 수동 취소: 조회로 확정 취소를 원장에 가져온 뒤 취소 ID와 확인 메모를 기존 환불에 연결한다. 같은 금액의 미연결 취소만 사용할 수 있다.
- 결제사에서 미처리 확인: 진행 중 취소가 없고 원래 잔액 그대로인 경우, 확인 근거를 기록하고 보류를 종료할 수 있다. 실제 미처리 확인 후에만 새 환불 요청을 만든다.
- 주문과 금액·채널이 불일치: 확인 필요 상태로 출고를 막는다. 서버 정보가 일치하고 보류 환불 결과를 확인한 뒤 대조 완료 메모를 남긴다. 결제 대조가 끝나면 회수·검수한 반품·교환 신청도 계속 처리할 수 있다.

결제사 관리자에서 쇼핑몰 신청과 무관하게 한 취소는 금액 원장에 반영하고 확인 필요 표시를 붙인다. 배송 후 수동 환불의 실물 반품은 자동 추정하지 않는다. 운영자가 신청 연결 또는 재고 조정으로 실제 회수 수량을 기록한다.

## 교환

교환 신청 → 승인 → 회수·검수 → 교환 운송장 등록 순서다. 교환품 발송에서 대상 옵션의 현재 재고를 검사하고 차감한다. 기존 회수품은 재판매 가능으로 검수한 경우에만 재고에 더한다. 품절로 실패하면 교환 수량과 재고 작업 전체를 되돌린다.

교환 출고는 원주문에 새 상품 행으로 연결하여 추적한다. 교환품도 다시 반품·교환할 수 있고, 새 매출로 중복 집계하지 않는다. 교환 차액 및 추가 배송비의 별도 PG 청구는 제공하지 않는다.

회수 후 교환품이 품절이면 고객과 확인한 사유를 기록하고 반품·환불로 전환할 수 있다. 검수 후 신청을 거절할 경우에도 사유와 회수품 반환 방법을 기록한다. 거절 자체는 재고나 결제 금액을 변경하지 않는다.

## 정산

정산은 **세금 신고용 확정 회계장부나 PG 입금 자동 조회가 아닌 운영 대조 화면**이다. 결제사 정산서와 실제 통장 입금 내역을 입력하여 차이를 확인한다.

- 조회 기간은 한국 시간, 시작일 00:00 이상·종료일 다음 날 00:00 미만이다.
- 결제 금액과 환불 금액은 승인·취소 시각 기준으로 따로 집계한다. 테스트 거래는 운영 집계에 포함하지 않는다.
- 판매 수량은 최초 승인 주문의 수량, 취소 수량은 출고 전 전액 취소 수량, 반품·교환 수량은 그 기간에 완료된 수량이다. 서로 다른 기간의 주문이 포함될 수 있으므로 단순히 뺀 값을 당일 순판매 수량이라고 해석하지 않는다.
- 상품별 수량과 상품 금액을 제공하고 배송비는 결제 합계에 포함한다.
- 정산서의 승인·환불·수수료(부가세 포함)·조정액·실입금을 입력한다. `입금 예정액 = 승인 − 환불 − 수수료 + 조정액`으로 계산한다.
- 입금 차이와, 정산서 매출 기간·PG별 원장 대비 승인/환불 차이를 따로 보여준다. 결제사 집계 기준·이월 내역은 메모로 남긴다.
- 환경·PG·정산 번호 중복 등록을 막고, 수정 시 이전 금액을 이력으로 남긴다.
- CSV는 결제 원장만 내보낸다. 배송지·연락처를 넣지 않으며 스프레드시트 수식 주입을 방지한다.

## 백업과 테마

쇼핑몰 스키마 판은 `modules/shop/src/Schema.php`의 `VERSION = 1`이다. 각 결제 플러그인도 자체 설치 레지스트리를 사용한다. 코어 DB의 구조를 바꾸지 않으므로 코어 `Schema::VERSION`과 제품 `version.txt`는 변경하지 않는다.

전체 백업에는 설치 레지스트리의 쇼핑몰·결제 설정 테이블과 기존 업로드 경로의 상품 이미지가 포함된다. 암호화에 사용한 `auth.secret`을 함께 보존해야 한다. 과거 주문의 조회·환불을 위해 결제 설정의 이전 판을 보관한다. SQLite 복원 후 API 실행 허용은 해제된다. 거래·재고를 결제사와 대조하고 API 실행을 다시 허용한다. 요청 중에는 백업·복원과의 공통 잠금을 유지한다.

같은 PortOne 상점에서 API Secret·웹훅 시크릿을 교체하면 과거 주문도 최신 인증키를 사용한다. 주문 당시의 채널·금액·환경 검증은 유지한다. 상점 ID 자체를 바꾼 경우에는 과거 상점 인증값을 보존하므로 이전 상점을 폐쇄하기 전에 남은 주문·환불을 처리한다.

선택 테마의 `extensions/shop/page.php`를 제공하면 그 디렉터리의 쇼핑몰 템플릿을 우선 사용하고 없는 파일은 모듈 기본값으로 보완한다. 결제 설정 화면은 `extensions/payment/settings.php`로 재정의한다. 코어 공통 partial과 기본 테마를 수정하지 않아 다른 CMS 화면에 영향을 주지 않는다.

## 검증과 운영 전 확인

```sh
./vendor/bin/phpunit tests/Shop
./vendor/bin/phpunit tests/Payment
./vendor/bin/phpunit tests/Web/ShopTest.php
./vendor/bin/phpunit
PUPPETEER_MODULE=/설치경로/puppeteer-core CHROME_BIN=/설치경로/chrome node tests/Browser/Shop.cjs
```

DB 테스트는 `connectionProvider`로 SQLite·MySQL/MariaDB·PostgreSQL을 실행한다. 동시 주문, 금액·채널 변조, 중복 콜백, 부분·전체 취소, 반품 수량, 교환품 재반품, 통신 단절·재요청 한도, 외부 환불 연결, 날짜 경계와 정산 차이를 검증한다. 브라우저 테스트는 외부 SDK를 대체하고 실제 결제 요청을 보내지 않는다.

테스트 결제와 실제 승인·취소는 구분해야 한다. 운영 개통 전 각 PG 채널에서 PC와 모바일의 승인, 부분·전체 취소, 서명된 웹훅 수신, 실제 정산서 대조를 수행한다. 이 저장소 테스트에는 가맹점 실계정·실카드가 없으므로 실제 거래의 성공을 보증하지 않는다. 결제사의 부분 취소 횟수·가능 기간과 계약상 제한은 사용하는 채널의 최신 문서를 확인한다.
