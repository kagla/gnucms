# 작은 쇼핑몰 운영 안내

한 사람이 상품·재고·배송·반품·정산을 관리하는 회원 전용 쇼핑몰이다. 상품 조회와 장바구니는 로그인 없이 사용할 수 있고, 주문·배송지·신청 내역은 해당 회원과 전역 관리자에게만 공개한다.

## 패키지와 결제 방식

| 패키지 | 역할 | 실행 주소 |
| --- | --- | --- |
| `modules/shop` | 상품, 주문, 배송, 반품·교환·환불, 재고, 정산 | 사용자 `/shop` · 관리자 `/admin/shop` |
| `plugins/payment-inicis` | KG이니시스 카드결제 | `/plugins/payment-inicis/settings` |
| `plugins/payment-kcp` | NHN KCP 카드결제 | `/plugins/payment-kcp/settings` |
| `plugins/payment-kspay` | KSPay / KSNET 카드결제 | `/plugins/payment-kspay/settings` |
| `plugins/payment-toss` | 토스페이먼츠 카드·간편결제 | `/plugins/payment-toss/settings` |

**PG에 직접 연동한다. 리셀러 코드는 가맹점 등록용이고, 결제 요청에는 등록 후 발급받은 상점 코드를 사용한다.** 별도 결제 중계 서비스의 계정·채널 키는 사용하지 않는다.

현재 구현 범위:

| PG | 설정 | 상태 |
| --- | --- | --- |
| 이니시스 | MID, 웹표준 SignKey, 모바일 Hash Key, INIAPI Key, 서버 IPv4 | PC·모바일 승인, 서버 조회, 전체/부분 환불 코드 구현. 가맹점 실연동 검증 필요 |
| KCP | site_cd, 서비스 인증서·개인키 PEM, 개인키 비밀번호 | 거래 등록·승인·취소 코드 작성. 조회 서명 규격 미확인으로 결제 실행 차단 |
| KSPay | MID, pgapi 인증키 | 직접 취소 코드 작성. 결제창·승인·조회 규격 미확보로 결제 실행 차단 |
| 토스페이먼츠 | MID, API 개별 연동 클라이언트 키(ck)·시크릿 키(sk) | PC·모바일 카드·간편결제창, 서버 승인·조회, 전체/부분 환불 구현. 가맹점 실연동 검증 필요 |

KCP 공개 조회 문서는 `kcp_sign_data` 서명식에 `mod_type`을 포함하지만 해당 값과 요청 항목을 명시하지 않는다. 공식 공개 테스트 인증서로 임의의 존재하지 않는 주문번호를 조회했으나 `S032`(접근권한 없음)로 거부되었다. 서명 규격 및 조회 API 권한 확인 전에는 구현 완료로 취급하지 않는다. KSPay는 KSNET의 해당 계약용 결제창·서버 승인·조회 문서와 샘플이 필요하다. 공개 REST의 카드번호 직접 입력 API는 일반 결제창을 대체하지 않는다.

각 플러그인은 `gateway.v2` 서비스를 제공한다. 쇼핑몰은 활성화하고 준비가 완료된 결제사만 선택할 수 있다. 결제 범위는 **KRW 일반 과세 카드결제와 전체·부분 취소**이며 토스페이먼츠 통합결제창의 간편결제도 지원한다. 카드번호를 GNUCMS에서 입력받거나 저장하지 않는다. 가상계좌, 계좌이체, 휴대폰, 빌링, 에스크로, 면세·복합과세, 쿠폰·적립금, 차액 결제는 포함하지 않는다. 교환은 동일 상품의 동일 가격 옵션으로 처리한다.

## 설치와 판매 시작

1. 관리자 → 플러그인에서 사용할 결제 플러그인을 활성화한다.
2. 결제 플러그인 설정에서 **데이터 설치**를 실행한다. GET 조회만으로 테이블을 설치하지 않는다.
3. 이니시스 테스트 환경에 발급받은 MID와 세 종류의 인증키, 서버 IPv4 주소를 저장한다. API 실행을 허용한다. SignKey와 INIAPI Key는 서로 다른 키다. 토스페이먼츠는 아래의 상점별 MID·API 개별 연동 키를 저장한다.
4. 관리자 → 모듈에서 작은 쇼핑몰을 활성화하고 **쇼핑몰 데이터 설치**를 실행한다.
5. 상점 설정에서 상호·대표자·사업장·연락처·반품 주소와 실제 운영에 맞는 배송·반품·개인정보 처리 정책을 입력한다. 개인정보 보관기간 및 결제·택배 위탁 정보도 운영 정책에 명시한다.
6. `config/config.php`의 `app.url`을 외부에서 접근 가능한 HTTPS 사이트 주소로 설정한다. 하위 경로 설치는 `https://example.com/cms`처럼 경로까지 포함한다.
7. 상품을 등록하고 관리자로 테스트 주문, PC·모바일 인증 결과 수신과 서버 승인, 부분·전체 취소를 검증한다. 테스트 상점에서는 관리자만 주문·결제할 수 있다.
8. 운영용 상점 코드와 인증 정보를 별도로 저장하고 API 실행을 허용한 뒤 상점의 결제 환경을 운영으로 바꾼다. 주문 접수를 연다.
9. 사이트 상단 메뉴와 모바일 전체 메뉴에 자동으로 표시되는 **작은 쇼핑몰**을 눌러 사용자 화면을 확인한다. 관리자 → 모듈에 표시되는 **사용자 화면: /shop** 주소에서도 열 수 있으며, 주소 옆 새 창 아이콘을 누르면 새 창으로 열린다. 모듈을 끄면 공개 메뉴도 사라진다.

운영 서버에서 Composer·npm 설치나 빌드를 하지 않는다. PHP 코드와 정적 템플릿은 배포본에 포함하고, 이니시스 PC와 토스페이먼츠 결제창에서 PG 공식 스크립트를 읽고, 이니시스 모바일 결제는 PG 결제창으로 폼을 전송한다. 주문·정산 화면의 PHP·CSS에는 새 패키지 의존성이 없다. 이미지와 런타임 잠금은 `storage/` 또는 기존 업로드 설정 경로에 저장한다.

## 구매자 화면

사용자 상점 주소는 `/shop`이다. 장바구니는 `/shop/cart`, 주문서는 `/shop/checkout`, 내 주문은 `/shop/orders`, 관리는 `/admin/shop`을 사용한다. 하위 경로 설치는 `/cms/shop`처럼 설치 경로를 앞에 붙인다.

사용자 주소와 관리자 주소는 패키지에 기본 설정되어 있다. 사용자 기본 주소는 `modules/shop/extension.json`의 `"route_prefix": "/shop"`에서 지정하며 패키지 ID·폴더는 `modules/shop`으로 유지한다. 사용자 내부 링크·로그인 복귀·결제 콜백도 이 값을 사용한다. 관리자 기본 주소는 같은 파일의 `"admin_route_prefix": "/admin/shop"`에서 지정한다. 이전 `/shop/products`, `/modules/shop/products` 등 관리 화면의 GET은 새 관리자 주소로 이동하고 기존 POST는 관리자 권한·CSRF 검사를 거쳐 처리한다. 기존 `/modules/shop/...` 주소는 같은 처리기로 계속 연결하므로 이전 폼과 결제 콜백도 처리된다. `/shop/`과 `/shop/catalog`도 상품 목록을 제공한다. 다른 짧은 주소로 바꿀 때는 사이트 내부의 사용하지 않는 영문 경로를 지정하고, 진행 중인 결제의 이전 짧은 콜백 주소를 임의로 없애지 않는다. 이 설정 파일은 패키지 파일이므로 배포 시 변경값을 함께 관리한다.

- **상품**: 비회원도 검색, 상세 설명, 옵션별 가격·재고와 품절 상태를 확인할 수 있다.
- **장바구니**: 옵션과 수량을 담고 수량 변경·삭제, 상품·배송비 합계를 확인한다. 비회원 장바구니는 이메일·소셜 로그인 뒤에도 유지된다.
- **주문 확인**: 로그인이 필요하면 인증 화면으로 이동하고, 성공 후 주문서로 돌아온다. 배송 정보·결제사·정책 동의를 확인한 뒤 주문을 만들고 주문 상세에서 결제한다. 판매 준비 중이거나 결제사가 준비되지 않았다면 주문 버튼을 비활성화한다.
- **내 주문**: 상점 메뉴, 사이트 계정 메뉴, 회원정보 수정의 **나의 쇼핑**에서 접근한다. 본인 주문을 상태별로 조회하고 배송·환불 내역, 미결제 취소, 배송 전 취소 신청, 반품·교환 신청을 확인한다. 다른 회원의 주문은 조회하거나 변경할 수 없다.

로그인 복귀 주소는 서버에서 선택한 사이트 내부 경로만 사용하며 30분 동안 한 번 유효하다. 로그인 실패 뒤에도 유지하고 성공 또는 로그아웃 시 비운다. 테스트 상점의 일반 구매자에게는 판매 준비 안내를 표시하고 관리자는 테스트 주문을 진행할 수 있다.

## 토스페이먼츠 설정

토스페이먼츠 개발자센터에서 결제창 서비스의 **상점아이디(MID)** 를 선택하고 **API 개별 연동**의 클라이언트 키와 시크릿 키를 함께 등록한다. API 버전은 **2022-11-16**을 선택한다. SDK는 V2 `payment().requestPayment()` 방식이며, 공식 문서에서는 이 통합결제창을 현재 “결제창(구버전)”으로 표기한다. 별도의 결제 중계 서비스 가입은 필요하지 않다.

- 테스트 환경은 `test_ck_…`·`test_sk_…`, 운영 환경은 `live_ck_…`·`live_sk_…` 쌍을 사용한다. 환경이 섞이거나 주문서형·결제창형 연동 키(`gck/gsk`)를 입력하면 저장을 거절한다.
- MID는 응답의 상점을 확인하는 기준이다. 결제창은 클라이언트 키, 서버 승인·조회·환불은 시크릿 키로 해당 MID에 연결한다. 리셀러 코드를 승인 요청에 넣지 않는다.
- 같은 MID에서 비워 둔 키는 기존 값을 유지한다. 저장 후에는 API 실행을 다시 허용한다. 시크릿 키는 암호화하고 브라우저에는 공개 클라이언트 키만 전달한다.
- PC·모바일 모두 `https://js.tosspayments.com/v2/standard`의 카드·간편결제창을 연다. 금액·주문번호는 저장된 주문에서 만들고 구매자 식별값은 서버 HMAC으로 생성한다.
- 인증 성공 URL은 `/shop/toss-return?id=…&state=…`다. GET 화면은 HMAC·주문번호·금액을 검사하고 `/shop/callback`으로 POST한다. 이전 `/modules/shop/toss-return`과 `/modules/shop/callback`도 계속 처리한다. 자바스크립트가 꺼져 있으면 확인 버튼으로 진행한다. GET만으로 승인하지 않으며 복귀 화면은 외부 자산을 읽지 않고 캐시·리퍼러 전송을 막는다.
- 서버는 `/v1/payments/confirm`으로 승인하고 `/v1/payments/orders/{orderId}`로 다시 조회한다. MID·주문번호·거래키·KRW·총액·잔액·승인 시각·결제수단·취소 내역이 일치할 때만 주문과 원장에 반영한다. 승인 응답을 받지 못했어도 주문번호 조회로 복구한다.
- 취소 전 PG 잔액과 부분 취소 가능 여부를 조회한다. 취소 요청에 금액, 예상 잔액(`refundableAmount`), `Idempotency-Key`를 보내고 응답에서 새 취소 ID 한 건과 금액을 대조한다. `refundableAmount`는 공식 문서에서 deprecated로 표시되어 있으나 현재 지원하는 추가 잔액 검사 항목이다. 응답이 불확실하면 자동 재전송을 막고 기존 관리자 대조 절차를 사용한다.
- 가상계좌 입금, 빌링, 에스크로·면세 상점은 이번 연동 범위에 포함되지 않는다. 정산 화면의 토스페이먼츠 필터와 입금 대조는 기존 확정 결제·환불 원장을 사용하며 PG 정산서 자동 수집은 제공하지 않는다.

## 상품과 옵션

테마 재정의는 `extensions/shop/products.php`(목록), `extensions/shop/product-form.php`(등록·수정)를 사용한다. 공통 관리 틀은 `page.php`, 상품 조합 입력 동작은 빌드 없이 제공되는 `shop-admin.js`를 사용한다. 기존 통합 `products.php` 재정의는 목록용으로 갱신해야 한다.

- 상품별 옵션 종류는 최대 두 개다. 예: 색상과 사이즈.
- 종류별 값은 쉼표로 구분한다. 각 종류는 20개 값까지, 전체 조합은 100개까지다. 옵션을 사용하지 않으면 이름과 값을 비운다.
- 상품 목록은 `/admin/shop/products`, 등록은 `/admin/shop/products/new`, 수정은 `/admin/shop/products/edit?id=…`로 분리한다. 목록에서 검색·옵션 제목·판매 상태·최저 판매가·재고를 확인하고 등록 또는 수정 화면으로 이동한다. 옵션 제목에 마우스를 올리면 `색상: 검정, 흰색`처럼 등록된 값이 표시된다. 품절 옵션도 포함하며 제거된 조합은 제외한다. 옵션이 없는 상품은 **없음**으로 표시한다.
- 등록·수정 화면에서 옵션 이름·값과 새 조합의 기본 판매가·초기 재고를 입력하고 **옵션 조합 적용**을 누른다. 표에 생성된 각 조합의 **최종 판매가**와 **판매 가능 재고**를 다르게 입력할 수 있다. 예: 검정/M 12,000원·3개, 흰색/L 18,000원·7개. 가격은 추가금이 아니라 해당 조합의 상품 가격이며 재고 0은 품절이다.
- **상품 저장**으로 기본 정보, 모든 옵션, 이미지와 순서를 함께 저장한다. 조합 적용은 저장하지 않으며, 이미 입력한 조합의 가격·재고를 유지한다. 자바스크립트가 꺼져 있어도 서버에서 조합 표를 생성한다. 새 조합의 기본값을 변경해도 기존 조합에는 일괄 적용하지 않는다.
- 판매가·재고 입력칸 옆 **아래 화살표**는 해당 칸의 현재 값을 아래 모든 조합의 같은 항목에 복사한다. 판매가와 재고는 각각 적용하며 위쪽 조합은 유지한다. 재고 0도 복사할 수 있다. 마지막 행은 복사할 대상이 없어 버튼을 비활성화하며, 실제 반영은 **상품 저장**을 눌렀을 때 이루어진다.
- 조합 누락·중복·음수 가격/재고·다른 상품의 옵션을 서버에서 거절한다. 수정 화면을 연 뒤 주문이나 재고 변경이 발생했다면 전체 저장을 취소하므로 새로고침 후 재고를 확인한다. 과거 주문 가격은 유지하고 변경 수량은 재고 원장에 기록한다.
- 상품명은 텍스트로 저장하고 출력 시 이스케이프한다. 상품 설명은 기존 내용 관리용 CKEditor로 제목·굵게·목록·표·링크·본문 사진을 편집한다. 설명은 선택 입력이며 HTML을 포함해 15,000자까지다. 서버에서 HTML을 정화하고 상세 화면에서도 공통 본문 렌더러를 사용한다. 기존 텍스트의 줄바꿈은 유지한다.
- 설명의 **사진 올리기**는 기존 본문 이미지 업로드를 사용한다(JPG·PNG·GIF·WebP, 기본 5MB). 편집 창마다 업로드 묶음을 분리하며, 옵션 조합 적용·저장 오류에서는 설명과 업로드 정보를 유지한다. 상품 저장 성공 후 현재 묶음에서 본문에 사용하지 않은 파일만 정리한다. 본문 사진은 갤러리와 별도로 관리하며 전체 백업의 에디터 이미지 폴더에 포함된다.
- **새 조합 기본 원가**와 조합별 **원가(원)**를 입력한다. 원가는 상품 한 개 기준 0 ~ 100,000,000원이며, 빈칸은 미입력으로 저장하고 0원과 구분한다. 옵션이 없으면 기본 상품 행에 입력한다. 원가 옆 아래 화살표로 아래 조합에 복사할 수 있다. 새 조합 기본 원가는 기존 조합을 덮어쓰지 않는다.
- 상품 저장으로 원가도 함께 반영한다. 주문은 생성 당시 옵션 원가, 교환품은 교환 출고 당시 원가를 별도로 보존한다. 이후 상품 원가를 수정해도 과거 주문은 바뀌지 않는다. 원가는 관리자 상품·정산 화면에서만 사용하며 고객용 상품·장바구니·주문 데이터에는 포함하지 않는다.
- 상품 이미지 갤러리는 최대 20장, 각 JPG·PNG·WebP 파일은 5MB 이하, 가로·세로 8,000px 이하를 지원한다.
- 삭제 대신 공개/비공개와 옵션 사용 상태로 관리한다. 과거 주문은 주문 당시 상품명·옵션·단가·배송비를 보존한다.
- 장바구니는 최대 20개 옵션, 옵션별 99개다. 모든 금액은 정수 원으로 계산한다.

## 상품 이미지

등록·수정 화면의 **상품 이미지 → 이미지 선택**에서 여러 파일을 선택한다. 저장 전 미리보기에서 새 이미지의 선택을 취소하거나 다시 선택해 추가할 수 있다. **상품 저장** 한 번으로 상품 정보·옵션·이미지·순서를 함께 반영한다. 파일 또는 순서 검증이 실패하면 상품·옵션 변경과 이번 업로드 전체를 취소하고 기존 데이터를 유지한다. 서버 검증 오류나 자바스크립트 없는 옵션 조합 적용으로 화면을 다시 받았을 때에는 새 이미지 파일을 다시 선택한다. 서버의 업로드 용량·개수 한도에 걸리면 나누어 저장한다.

기존 이미지와 선택한 새 이미지 모두 이동 손잡이나 이미지를 드래그해 순서를 바꾸고 **상품 저장**을 누른다. 모바일에서는 이동 손잡이를 터치해 끌며, 이전·다음 버튼이나 손잡이의 키보드 방향키로도 조정한다. 맨 앞 이미지가 목록·장바구니의 대표 이미지가 되고 상품 상세 갤러리도 저장한 순서대로 표시한다. 다른 화면에서 상품·이미지를 바꿨다면 새로고침 후 다시 저장한다.

테마 재정의는 `extensions/shop/product-form.php`와 `extensions/shop/_product-images.php`(관리), `extensions/shop/product.php`(상세)를 사용한다. `shop-admin.css`, `shop-images.js`, `shop-gallery.js`는 배포본에 포함하는 정적 자산이며 빌드가 필요 없다. 관리 이미지 partial은 상품 폼 내부의 입력 영역이므로 별도 `<form>`을 만들지 않는다. 기존 테마에서 이미지 업로드·순서 폼을 재정의했다면 통합 폼에 맞게 갱신한다. 이미지 목록과 순서는 DB, 원본은 업로드 폴더의 `shop/`에 저장하므로 전체 백업·복원에 함께 포함된다.

## 주문과 재고

```text
결제 대기 → 결제 완료 → 상품 준비 → 배송 중 → 배송 완료
    └ 주문 취소             └ 배송 전 전액 환불
                                      배송 후 → 반품·교환 신청
```

주문 생성 시 가격과 배송비를 서버에서 다시 계산한다. 사용자가 확인한 금액과 다르면 주문을 거절하고 다시 확인하도록 안내한다. 정책 동의 시각과 당시 정책을 주문에 보존하며, 배송지는 암호화한다.

재고는 주문 생성 시 확보한다. 옵션의 판 번호와 재고를 조건부 SQL로 함께 검사하므로 마지막 한 개에 동시 주문이 들어와도 한 주문만 확보한다. 장바구니에 담은 시점에는 확보하지 않는다. 대기 주문은 회원당 다섯 개까지다.

결제 기한은 30분이다. 새 주문 생성 시와 관리자의 미결제 정리 작업에서 만료 주문을 정리한다. 방문과 관계없이 정리하려면 다음 CLI를 스케줄러에서 실행한다. 한 번에 최대 100건을 처리한다.

```sh
php modules/shop/bin/maintenance.php expire
```

취소·만료된 주문에서 늦게 승인이 도착하면 출고하지 않고 같은 요청 키로 전액 취소한다. 취소 결과가 불명확하면 재고를 다시 확보하지 않고 확인 필요 상태로 보존한다. 이미 전송한 취소 요청은 응답이 끊겨도 자동 재전송하지 않는다. 확인되지 않은 지연 취소는 운영자가 PG 내역을 확인해야 한다.

재고 화면은 판매 가능 수량, 주문 확보 수량, 출고 전 보유 합계를 보여준다. 최근 100건의 초기 입고·수정·주문·취소·반품·교환 변동을 함께 확인할 수 있다. 재고 수정 도중 새 주문이 발생하면 오래된 화면의 수량 덮어쓰기를 거절한다.

재고 화면의 최근 수량 변동에는 일시·상품/옵션·사유·변동 수량을 표시한다. 내부 참조값인 `reference`는 화면에 표시하지 않고 변동 원인이 된 상품·주문·반품·교환을 추적하는 기록으로 보존한다. 각 재고 변동 기록의 기본키는 별도 `id`다.

## 결제 검증과 인증 결과

브라우저에는 서버에 저장한 주문번호와 금액으로 생성한 PG 결제창 정보만 전달한다. 이니시스는 PC 요청 해시·보안 검증값과 모바일 금액 위변조 해시를 생성한다. 브라우저의 인증 성공만으로 주문을 결제 완료 처리하지 않는다.

인증 결과는 다음 경로로 전달된다. `state`는 주문·PG·설정 판에 묶인 HMAC 값이다. 세션 쿠키에 의존하지 않으므로 외부 결제창에서 돌아오는 POST도 처리한다.

```text
https://example.com/shop/callback?id=<주문번호>&state=<검증값>
```

콜백은 URL 인코딩 폼만 허용하고 본문은 64KB로 제한한다. 중복 키·배열 입력을 거절한다. 인증기 통과 후 PG 서버에 승인 요청을 보내며, 상점·주문·금액·카드 수단을 검증한다. IDC 코드와 승인 URL의 고정 호스트를 대조한다. 승인 응답이 유실되거나 검증에 실패하면 이니시스 망취소를 시도한다.

서버 조회는 상점 코드, 주문번호, 거래번호, 결제 금액, 원화 통화, 카드 수단, 승인 시각 및 누적 취소 내역을 확인한다. 값이 다르면 출고·정산 확정을 보류한다. 승인·환불 요청을 보내기 전에 DB에 처리 상태를 저장하고, 같은 요청을 다시 보내지 않는다. 카드번호·인증 토큰·PG 응답 원문은 기록하지 않는다.

이니시스 승인 TID를 받지 못한 요청의 복구 조회에는 **주문번호 중복방지 계약**이 필요하다. 상점의 해당 계약과 조회 API 사용 권한을 개통 전에 확인한다. 승인 결과가 불확실한 주문은 새 결제를 시작하지 않고 PG 내역을 먼저 확인한다.

API 대상은 고정 HTTPS 호스트이며 TLS 인증서를 검증하고 HTTP 리다이렉트를 따르지 않는다. 각 요청의 응답 대기는 60초다. API 실행 허용을 해제하면 신규 결제와 조회·환불을 정지한다. 플러그인 사용 중지와 기존 주문 환불 완료 여부를 함께 확인한다.

승인 후 브라우저 복귀가 중단되면 주문의 **결제·환불 상태 조회**를 사용한다. 정기적으로 미확정 주문을 조회하려면 다음 명령을 사용한다. 최근 7일간 결제창을 연 대기·취소 주문, 확인 필요 주문, 보류 환불을 오래 조회하지 않은 순서대로 처리한다.

```sh
php modules/shop/bin/maintenance.php reconcile --limit=20
php modules/shop/bin/maintenance.php sync --order=<주문번호>
```

별도 설정 파일은 `--config=/절대경로/config.php`로 지정한다. 명령은 쇼핑몰 활성 상태와 API 실행 허용을 존중한다. 스케줄러에 5~10분 간격으로 등록할 수 있으며, CLI 오류는 주문·연결 정보를 노출하지 않는다.

## 취소·반품·환불

배송 전에는 고객이 취소 신청을 하거나 운영자가 전액 취소할 수 있다. 열린 취소 신청이나 미확정 환불이 있으면 출고를 막는다.

상품 준비·출고와 교환품 발송 직전에 결제사 상태를 다시 조회한다. 외부 취소나 진행 중 취소가 확인되면 출고하지 않고 결제 대조를 요구한다.

반품은 다음 순서로 처리한다.

1. 고객 또는 운영자가 주문 상품과 수량, 사유를 지정해 접수한다.
2. 운영자가 승인하거나 사유와 함께 거절한다. 거절하면 다시 신청할 수 있다.
3. 회수·검수 완료를 기록하고 재판매 가능 여부를 선택한다.
4. 반품 상품 금액을 확인하고 최초 배송비 환불 여부, 정책에 따라 고객과 확인한 반품 비용 공제액을 지정한다.
5. 환불을 요청한다. 서버 조회로 취소가 확정된 뒤에만 반품 완료 수량과 재판매 가능한 재고를 반영한다.

환불 금액은 `주문 당시 단가 × 반품 수량 + 선택한 최초 배송비 − 반품 비용`이다. 최초 배송비는 한 번만 환불할 수 있다. 누적 환불이 결제 금액을 초과하거나 이미 처리·신청한 수량을 다시 신청하는 것을 거절한다. 반품 비용이 상품 환불액 이상인 0원 환불은 지원하지 않는다.

환불 요청은 외부 호출 전에 DB에 저장한다. 이니시스 부분 취소에는 취소 후 예상 잔액을 전달한다. 동일 요청 키로 다른 금액이나 사유를 보낼 수 없다. PG가 공통 멱등 키를 지원한다고 가정하지 않으며, 전송한 요청은 자동 재전송하지 않는다.

- 정상 응답: 서버 조회로 취소를 대조한 뒤 기존 반품·환불을 완료한다.
- 응답 유실: PG 관리자에서 결과를 확인한다. 실제 성공했다면 주문 화면의 수동 취소 연결에 확정 취소 ID와 확인 메모를 입력한다. 서버 조회에서 ID·금액이 일치하는 취소만 연결할 수 있다.
- 미처리 확인: 2시간 경과 후 PG에서 미처리를 확인한 근거를 기록한다. 서버 조회 잔액이 원래 값과 같을 때만 보류를 종료하고 새 요청을 만들 수 있다.
- 외부 취소: 서버 조회에서 가져온 미연결 취소를 기존 신청에 연결한다. 같은 취소를 여러 신청에 재사용할 수 없다.
- 주문·상점·금액 불일치: 확인 필요 상태를 유지한다. 서버 정보와 미확정 환불을 대조한 뒤 관리자가 근거를 기록한다.

결제사 관리자에서 쇼핑몰 신청과 무관하게 한 취소는 금액 원장에 반영하고 확인 필요 표시를 붙인다. 배송 후 수동 환불의 실물 반품은 자동 추정하지 않는다. 운영자가 신청 연결 또는 재고 조정으로 실제 회수 수량을 기록한다.

## 교환

교환 신청 → 승인 → 회수·검수 → 교환 운송장 등록 순서다. 교환품 발송에서 대상 옵션의 현재 재고를 검사하고 차감한다. 기존 회수품은 재판매 가능으로 검수한 경우에만 재고에 더한다. 품절로 실패하면 교환 수량과 재고 작업 전체를 되돌린다.

교환 출고는 원주문에 새 상품 행으로 연결하여 추적한다. 교환품도 다시 반품·교환할 수 있고, 새 매출로 중복 집계하지 않는다. 교환 차액 및 추가 배송비의 별도 PG 청구는 제공하지 않는다.

회수 후 교환품이 품절이면 고객과 확인한 사유를 기록하고 반품·환불로 전환할 수 있다. 검수 후 신청을 거절할 경우에도 사유와 회수품 반환 방법을 기록한다. 거절 자체는 재고나 결제 금액을 변경하지 않는다.

## 정산

정산은 **세금 신고용 확정 회계장부나 PG 입금 자동 조회가 아닌 운영 대조 화면**이다. 결제사 정산서와 실제 통장 입금 내역을 입력하여 차이를 확인한다.

- 조회 기간은 한국 시간, 시작일 00:00 이상·종료일 다음 날 00:00 미만이다.
- 결제 금액과 환불 금액은 승인·취소 시각 기준으로 따로 집계한다. 테스트 거래는 운영 집계에 포함하지 않는다.
- 판매 수량은 최초 승인 주문의 수량, 취소 수량은 출고 전 전액 취소 수량, 반품·교환 수량은 그 기간에 완료된 수량이다. 서로 다른 기간의 주문이 포함될 수 있으므로 단순히 뺀 값을 당일 순판매 수량이라고 해석하지 않는다.
- 상품별 수량과 상품 금액을 제공하고 배송비는 결제 합계에 포함한다.
- 정산서의 승인·환불·수수료(부가세 포함)·조정액·실입금을 입력한다. `입금 예정액 = 승인 − 환불 − 수수료 + 조정액`으로 계산한다.
- 입금 차이와, 정산서 매출 기간·PG별 원장 대비 승인/환불 차이를 따로 보여준다. 결제사 집계 기준·이월 내역은 메모로 남긴다.
- 환경·PG·정산 번호 중복 등록을 막고, 수정 시 이전 금액을 이력으로 남긴다.
- **상품별 원가와 이익**은 선택 기간에 결제된 주문을 모아 **현재까지 확정된** 취소·반품·교환을 반영한다. 따라서 기간이 지난 뒤 처리된 반품도 해당 결제 기간의 상품 손익을 바꿀 수 있다. 승인·환불 원장의 처리일별 집계와 집계 기준이 다르다.
- 상품 실매출은 최초 상품 금액에서 상품에 연결된 확정 환불(배송비 제외)을 뺀 값이다. 합의한 반품 비용은 차감된 환불액에 반영된다. 소진 원가는 주문 및 교환 출고 수량의 보존 원가에서 재판매 가능한 회수품의 원가를 되돌린 값이다. 출고 전 전액 취소는 매출과 원가를 모두 되돌리고, 재판매 불가 회수품은 비용으로 남긴다. 교환 재출고는 매출을 추가하지 않는다.
- 상품 이익은 **상품 실매출 − 소진 원가**, 이익률은 **상품 이익 ÷ 상품 실매출 × 100**이다. 실매출이 0 이하이면 이익률은 표시하지 않는다. 수수료·실제 배송비·세금·기타 운영비를 제외한 상품 기준 이익이므로 최종 순이익은 아니다.
- 원가가 없는 과거 주문이나 미입력 상품을 0원으로 추정하지 않는다. 해당 소진 수량을 표시하고 원가·이익 계산을 보류한다. 상품에 연결되지 않은 외부 부분 환불도 임의 배분하지 않고 실매출·이익을 보류한다. 전액 환불은 상품 실매출이 0원으로 확정된다.
- CSV는 결제 원장만 내보낸다. 배송지·연락처를 넣지 않으며 스프레드시트 수식 주입을 방지한다.

## 백업과 테마

쇼핑몰 스키마 판은 `modules/shop/src/Schema.php`의 `VERSION = 4`이다. 옵션과 주문 상품에 nullable `cost_price`를 추가한다. 새 설치와 SQLite·MySQL/MariaDB의 기존 설치를 모두 지원하며, 갱신 전 상품과 주문의 원가는 미입력으로 남긴다. 중간 실패 후 재실행해도 이미 입력된 원가를 덮어쓰지 않는다. 3판에서는 상품 이미지 목록과 순서를 저장하는 `shop_product_images` 테이블을 추가하고 기존 대표 이미지를 첫 이미지로 옮긴다. 관리자 쇼핑몰 운영 화면의 **쇼핑몰 데이터 설치/갱신**을 실행한다. 갱신 전에도 기존 상품·주문 조회와 3판의 이미지 갤러리는 유지하며, 원가 입력과 손익 집계는 갱신 후 사용할 수 있다. SQLite는 갱신 전 자동 백업을 만들며, 중간 실패 후 재실행해도 기존 이미지와 순서를 보존한다. 이전 2판에서는 토스 거래키를 위해 주문의 거래번호와 금액 원장의 참조값을 최대 200자로 확장한다. 기존 쇼핑몰은 관리자에서 데이터 설치/갱신을 실행한다. MySQL/MariaDB는 두 컬럼을 멱등 확장하며, SQLite의 기존 VARCHAR에는 길이 제한이 없어 기존 테이블을 그대로 사용할 수 있다. 결제 플러그인 스키마 판은 2이며 암호화된 거래 처리 기록 테이블을 추가한다. 기존 설치에서는 결제 설정의 데이터 설치/갱신을 실행한다. 코어 DB의 구조를 바꾸지 않으므로 코어 `Schema::VERSION`과 제품 `version.txt`는 변경하지 않는다.

전체 백업에는 설치 레지스트리의 쇼핑몰·결제 설정·거래 처리 기록 테이블과 기존 업로드 경로의 상품 이미지가 포함된다. 암호화에 사용한 `auth.secret`을 함께 보존해야 한다. 과거 주문의 조회·환불을 위해 결제 설정의 이전 판을 보관한다. SQLite 복원 후 API 실행 허용은 해제된다. 거래·재고를 결제사와 대조하고 API 실행을 다시 허용한다. 요청 중에는 백업·복원과의 공통 잠금을 유지한다.

같은 PG 상점 코드에서 인증키나 요청 서버 IPv4 주소를 변경하면 과거 주문도 최신 설정을 사용한다. 주문 당시의 상점·금액·환경 검증은 유지한다. 상점 ID 자체를 바꾼 경우에는 과거 상점 인증값을 보존하므로 이전 상점을 폐쇄하기 전에 남은 주문·환불을 처리한다.

쇼핑몰 운영 화면은 기존 관리자 공통 레이아웃·글꼴·입력·버튼·표·다크 모드를 사용한다. 고객용 상품·장바구니·주문 화면도 사이트 공통 `layout`의 머리글·모바일 메뉴·다크 모드를 사용한다. 고객용 `shop.css`는 내용 해시가 붙는 정적 테마 자산이며 `.shop-storefront` 안에만 적용한다. 선택 테마의 `extensions/shop/` 아래 템플릿을 우선 사용하고 없는 파일은 모듈 기본값으로 보완한다. `page.php`는 운영/고객 화면을 선택하고 `storefront.php`는 고객 화면의 외곽을 구성한다. 개별 조각만 재정의할 수도 있다. 상품 원가 입력은 `product-form.php`, 정산의 상품 손익 표는 `_profit.php`를 재정의한다. 기존 상품 폼 재정의에서 원가 필드를 제출하지 않으면 저장된 옵션 원가를 보존한다. `orders.php`는 고객 주문 카드, `_orders.php`는 관리자 주문 표, `_seller.php`는 판매자·정책 안내를 담당한다. 테마에서 기존 `storefront.php`를 재정의했다면 공통 레이아웃과 `shop-storefront` 래퍼 적용을 함께 반영해야 한다. 주소를 직접 적지 말고 모듈 화면의 `url` 또는 공통 화면의 `public_extensions['modules/shop']['base_url']`에 하위 경로를 붙인다. 결제 설정 화면은 `extensions/payment/settings.php`로 재정의한다. 결제 설정 재정의는 PG별 `fields` 입력과 `integration_ready` 상태를 표시해야 한다. 주문 화면 재정의는 새 결제 폼 계약을 적용해야 한다. 토스는 `payment.kind=toss`의 `client_key`, `customer_key`, `request`로 SDK를 호출하며 JSON을 스크립트에 넣을 때 HTML 특수문자를 이스케이프한다. 인증 결과 전달 화면 `toss-return.php`는 모듈에서 직접 제공한다.

## 검증과 운영 전 확인

```sh
./vendor/bin/phpunit tests/Shop
./vendor/bin/phpunit tests/Payment
./vendor/bin/phpunit tests/Web/ShopTest.php
./vendor/bin/phpunit
PUPPETEER_MODULE=/설치경로/puppeteer-core CHROME_BIN=/설치경로/chrome node tests/Browser/Shop.cjs
PUPPETEER_MODULE=/설치경로/puppeteer-core CHROME_BIN=/설치경로/chrome node tests/Browser/Toss.cjs
PUPPETEER_MODULE=/설치경로/puppeteer-core CHROME_BIN=/설치경로/chrome node tests/Browser/ShopImages.cjs
```

DB 테스트는 `connectionProvider`로 SQLite·MySQL/MariaDB를 실행한다. 동시 주문, 금액·상점 변조, 중복 콜백, 부분·전체 취소, 반품 수량, 교환품 재반품, 통신 단절·재전송 차단, 외부 환불 연결, 날짜 경계와 정산 차이를 검증한다. 브라우저 테스트는 외부 SDK를 대체하고 실제 결제 요청을 보내지 않는다.

자동 테스트는 PG 응답을 대체한다. 이니시스·토스페이먼츠 운영 개통 전 가맹점 테스트 환경에서 PC·모바일 승인, 취소, 응답 유실 복구, 실제 PG 정산서 대조를 수행해야 한다. 현재 KCP·KSPay 연동은 미완성이므로 운영용으로 활성화할 수 없다.
